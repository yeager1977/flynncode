## Key Question 2: Prompt caching — pricing, mechanics, hit-rate, TTL

### Takeaway
xAI's API does **fully automatic, marker-free prefix caching with no cache-write fee**: cached input tokens bill at **0.25× the input price** (~75% discount) and are metered in **128-token blocks**, reported via `cached_tokens` in usage details. The discount is structural and considerable versus full price, though shallower than Anthropic's 0.1× cache-read rate — xAI compensates with zero write premium (Anthropic charges 1.25× on write) and no `cache_control` ceremony. Two agentic-specific facts stand out: (1) missing `reasoning_content`/encrypted reasoning from prior turns is "the top cause of cache misses" for reasoning models, so Grok's coding stack is built around always replaying encrypted reasoning; and (2) xAI's own cookbook demonstrates that a single dynamic line at the *top* of the system prompt (e.g., a changing timestamp) collapses cache hits from ~87% to ~3% and multiplies cost 2.3–2.9×.

### Cited Findings
- **Mechanism**: "When consecutive requests share the same starting messages, the xAI API automatically caches them… Cached tokens are billed at … a substantially lower rate"; xAI recommends the `x-grok-conv-id` HTTP header (Chat Completions) or `prompt_cache_key` (Responses/OpenAI-compat) "to maximize your cache hit rate" — [docs.x.ai/developers/advanced-api-usage/prompt-caching](https://docs.x.ai/developers/advanced-api-usage/prompt-caching) (updated 2026-03-16).
- **Cache breaks**: "For reasoning models, you must include `reasoning_content` from previous responses; omitting it is the top cause of cache misses." Recovery paths: send back encrypted reasoning content, or use stateful `previous_response_id`. The best-practices guide lists the three classic breakers (extracting only `output_text`; editing/reordering/filtering output items; rebuilding the transcript between turns) — [docs.x.ai prompt-caching/multi-turn](https://docs.x.ai/developers/advanced-api-usage/prompt-caching/multi-turn) and [docs.x.ai best-practices](https://docs.x.ai/developers/model-capabilities/text/best-practices).
- **Pricing by model** (per 1M, input / cached / output, short-context tier; docs.x.ai/developers/pricing, checked 2026-10-10 via BiWu mirror):
  - `grok-4.7` (500k ctx): $2.00 / **$0.50** / $6.00; long-context (≥200k prompt): $4.00 / $1.00 / $12.00.
  - `grok-build-0.1` (coding model, 256k ctx): $1.00 / **$0.20** / $2.00.
  - `grok-4.3` / `grok-4.20-*` variants (1M ctx): $1.25 / **$0.20** / $2.50.
  - Earlier fast models: `grok-4-1-fast` (2M ctx): $0.20 / **$0.05** / $0.50 ([x.ai/news/grok-4-1-fast](https://x.ai/news/grok-4-1-fast)); `grok-code-fast-1` at launch: $0.20 / **$0.02** / $1.50 ([x.ai/news/grok-code-fast-1 (2025-08-28)](https://x.ai/news/grok-code-fast-1)).
  - All models listed offer a cached-input discount ([BiWu check of docs.x.ai, Oct 10 2026](https://biwu.ai/en/api-pricing/provider/xai)).
- **Ratios vs competitors**: cached = 0.25× regular input on Grok with **0× write fee** and no caching markers; the APIYI capability note contrasts this with Claude (requires `cache_control` markers) and OpenAI (automatic but with per-model discounts), and contradicts common folklore by pointing out no `prompt_cache_key`-style routing guarantee — historically OpenAI's field name is where xAI now plumbed theirs ([docs.x.ai REST reference](https://docs.x.ai/developers/rest-api-reference/inference/chat) shows `prompt_cache_key` plumbed to `x-grok-conv-id`).
- **128-token block granularity**: "Caching works in blocks of 128 tokens. Every cached count was a multiple of 128, so the last partial block of a prompt is always new" — [docs.x.ai cookbook: prompt-caching example](https://docs.x.ai/cookbook/examples/prompt-caching).
- **Cache-hit-rate experiment in the official cookbook** (three parallel 30-turn chats over `grok-4.7`): time-in-message variant hit **87% cached input** at $0.117 total; the same chat with the (changing) timestamp "on top" of the system prompt hit only **3%** and cost **2.3×** more (2.2–2.9× across runs); an auto-compaction variant held 86% but cost 1.4× more than the plain-cached chat because compaction calls themselves bill at output price — [docs.x.ai cookbook/examples/prompt-caching](https://docs.x.ai/cookbook/examples/prompt-caching).
- **Compaction-vs-cache verdict from xAI's own experiment**: "Compaction cost more than it saved" at that workload scale — each 10,000 tokens removed saves ~half a cent per turn under caching, so compaction pays off only for chats whose turns are many times the summary size, or to stay within the context window. Summaries varied from 15 to 2,350 tokens and a 15-token summary forgot an essential fact; compacting the system prompt into the summary lost handbook content entirely ("Grok made up menu details") — same source.
- **TTL / eviction**: no fixed TTL is published. xAI states entries "may be evicted under memory pressure, on restart, or when a request lands on a different server" and recommends `prompt_cache_key`/`x-grok-conv-id` routing to the server holding the cache. In the cookbook's no-key ablation the API still cached 64–95% of input. Cache misses per-turn even with the key occurred while the API was busy — [cookbook](https://docs.x.ai/cookbook/examples/prompt-caching) and [docs.x.ai prompt-caching](https://docs.x.ai/developers/advanced-api-usage/prompt-caching).
- **Long-context pricing interplay**: once the prompt (including cached tokens) crosses the model's long-context threshold (200k for most current models), *all* tokens, cached and uncached, bill at long-context rates ([docs.x.ai pricing page](https://docs.x.ai/developers/pricing), last updated 2026-10-10). Priority Processing (2× for lower latency) applies after cache discounts; US regional endpoint (`us.api.x.ai`) is a 1.1× premium on everything including cached tokens ([docs.x.ai/developers/pricing](https://docs.x.ai/developers/pricing)).
- **Rate limits relevant to agents**: `grok-build-0.1` and `grok-4.20` at 37 requests/sec and 10,000,000 tokens/min on API rate tables ([docs.x.ai model pages](https://docs.x.ai/developers/models/grok-4.20)).

### Inferences
- For agentic workloads the cache hit rate is the dominant cost lever on Grok just as on Claude Code/Codex, and xAI's guidance implies their agent harness (and any target harness) should be engineered around a strictly append-only, byte-stable prompt prefix with system prompt high up and reasoning items replayed verbatim — Grok Build's OSS changelog even records a fix keeping "the prompt prefix… byte-stable and KV cache preserved" on resume ([xai-grok-shell changelog 0.2.41](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-shell/changelogs/0.2.41.md)).
- The 0.25× cached rate (vs Anthropic's 0.1×) is less generous per token, but with zero write cost and unconditional automation the break-even is the second request; and on the *coding* model the effective cached price ($0.20/1M on `grok-build-0.1`) is among the cheapest in the industry.

### Gaps
- No officially published cache eviction window (minutes/hours) was found; only qualitative statements.
- No official "hit-rate" SLA or guarantee exists; the 87%/3% figures are xAI's own cookbook measurements, not a product claim.

## Key Question 3: Model routing — fast/cheap variants vs flagship, context windows, reasoning-effort controls

### Takeaway
The current lineup (Oct 2026) pairs a flagship tier (`grok-4.7`, 500k context, reasoning effort low/medium/high/xhigh, default high) with an economical coding model (`grok-build-0.1`, alias lineage `grok-code-fast-1`, 256k) and mid/high-efficiency generalists (`grok-4.3`, `grok-4.20`, 1M). Routing happens four ways: (a) consumer "Auto mode" picks fast vs deep models per query; (b) **Grok Build's smart-auto** serves whichever model it deems suitable and (since v1.0.45) shows the actually-served model in the UI; (c) developers implement routing themselves via the API (reasoning-effort knobs, reasoning vs non-reasoning twins of fast models, choosing a cheaper/smaller model for compaction calls); and (d) xAI has a true multi-agent model variant (`grok-4.20-multi-agent`) for server-side deep research orchestration.

## Key Question 4: Harness techniques in the Grok Build coding agent (and community grok CLIs)

### Takeaway
Grok Build's documented harness economy rests on: **auto-compaction at ~85% context usage with a nine-section structured "successor brief"** (not ad-hoc "summarize this"), **byte-stable prompt prefixes to preserve cache**, **token observability at every level** (`/context` with per-source costs, `/usage`, persisted per-turn ledgers, OpenTelemetry export telling whenever the compaction actually saved), and **selectable context-window sizes per model/session**. Notably, it *lacks* tool-result truncation at ingest: hooks can only allow/deny tool calls (post-tool output cannot be rewritten by hooks), so big tool outputs ride along until compaction fires — a gap third parties fill with local LLM proxies. Subagents each carry their own context window, and memory features persist across sessions.

### Cited Findings
- **Compaction design** (independent deep-dive based on the open-source code): "Grok Build's main approach is full-replace: structured summary in, fat history out… Auto near ~85% of context, or `/compact`. Default: same chat model, tools off for the summary pass. The handoff is a **nine-section successor brief** (intent, files, errors, pending work, next step…), not a vague 'summarize please'" — [blog.visionik.com, "How Grok Build the harness works" (2026-07-16)](https://blog.visionik.com/how-grok-build-the-harness-works/).
- **Configurability**: `auto_compact_threshold_percent` under `[session]` (default 85); `context_window` per model drives auto-compact timing; `/compact [context]` takes optional keep-instructions; `/rewind`; `/new`; `/goal --budget <tokens>` caps unattended token spend — [Tokenade guide (2026-10-14)](https://tokenade.net/en/articles/reduce-grok-cli-token-usage).
- **Context-window selection** is a first-class feature: `/context-window` lets a user pick the window size for the current session when the model offers choices; the model catalog "advertises multiple context window sizes; the first listed value is the default"; downsizing "starts an auto-compact" — [changelog v1.0.44](https://x.ai/changelog/build) and [techdevnotes 1.0.45 summary](https://techdevnotes.com/releases/grok-build-src/97f190f644ae).
- **Observability**: `/context` shows pinned token costs "for skills and MCP servers" beside the usual categories (since v0.2.98); `/usage` shows persisted **per-turn token and cost** data (v1.0.14); headless JSON includes token+cost per prompt and session; SDK turns expose `Turn.usage`; OpenTelemetry exports `grok_code.token.usage` (split by input/output/**reasoning**/cache_read and model) and `grok_code.compaction` events with `tokens_before`/`tokens_after` — [changelog](https://x.ai/changelog/build), [Tokenade](https://tokenade.net/en/articles/reduce-grok-cli-token-usage).
- **Cache-prefix discipline in the harness**: the open-source shell changelog fixed "memory context injection on resume so **the prompt prefix stays byte-stable and KV cache is preserved**" (0.2.41) — [github.com/xai-org/grok-build 0.2.41 changelog](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-shell/changelogs/0.2.41.md). Related UI fixes: "Context estimates for conversations with reasoning are more accurate" and "Token usage after rewinding… matches the server-reported count" (v1.0.12).
- **Sub-agents**: "Each child runs in parallel with its own context window"; deep worktree support (subagents in their own `git worktree`s); bounded spawning (queued instead of file-descriptor exhaustion); subagent sessions resumable "for larger transcripts that still fit the model context"; subagent context-usage shown per agent ("Workflow agent rows display current context usage instead of cumulative token counts," v1.0.8) — [x.ai/build](https://x.ai/build), [changelog](https://x.ai/changelog/build).
- **No tool-result truncation at ingest**: "Grok Build supports hooks, but its PreToolUse hook can only allow or deny a call, and the output of PostToolUse is ignored. Nothing plugged in through hooks can fold a test log before the model reads it" — [Tokenade (2026-10-14)](https://tokenade.net/en/articles/reduce-grok-cli-token-usage). The same source catalogs what the settings *don't* change (UI-only compaction of the transcript does not affect what is sent). Tokenade's workaround: route Grok Build through a local proxy (loopback) that folds tool results per request before they reach the model API.
- **File-read cap**: skills and other reads are capped at **25k tokens**; oversized bodies show a truncation note (v1.0.33) — [changelog](https://x.ai/changelog/build).
- **Memory**: persistent session memory that "no longer blocks the agent during turn completion" (perf fix, v1.0.14); cross-session memory (disabled in one benchmark to prevent leakage); memory entries are "presented as historical context to verify against live sources" — [changelog](https://x.ai/changelog/build), [VulcanBench](https://vulcanbench.com/assets/reports/vulcanbench-grok46-grokbuild-report.pdf).
- **Goal mode** for long-running autonomy with a token budget, plus plan/todo/task tool surfaces: "Failed task and todo tool calls appear in the transcript"; `/workflow` child-agent budgets; per-goal token+time in `/goal status` — [ai-cost-estimator blog on /goal cost model (2026-06-23)](https://ai-cost-estimator.com/blog/xai-grok-build-goal-mode-long-running-autonomous-coding-cost-per-day), [Tokenade](https://tokenade.net/en/articles/reduce-grok-cli-token-usage), [changelog](https://x.ai/changelog/build).
- **Quantitative harness-tax measurements (third party)**: on six one-defect QuixBugs tasks ×12 runs, Grok Build (grok-4.6) reported **325,319 total tokens vs 19,981 for a bare thin-API loop** (16×, 93.9% of bill being pre-answer context) with quality identical (12/12 both); a minimal system-prompt override recaptured only **4.5%** of the gap, indicating most of the token difference sat in scaffold/passes other than the editable prompt — [Terry Li, "The Harness Is Part of the Token Bill" (2026-08-24)](https://terryli.ai/posts/the-harness-is-part-of-the-token-bill/).
- **Harness×effort interaction** (VulcanBench, 23 real post-cutoff PR tasks, grok CLI v1.0.5): Grok Build is the only harness where the effort knob is monotone (84.1 → 88.4 → 89.9 → 92.8% pass@1 from low → xhigh; peak 92.8 set a suite record and cost the raw API "14.5 points" at the same setting), while token use **nearly triples** (prompt tokens 40.4M → 112.4M) and API-equivalent cost rises $28.93 → $75.13; Grok Build finished high-effort tasks in median **4.5 min vs 16.3 min via the raw API** — [VulcanBench Grok 4.6 report (2026-08-12/18)](https://vulcanbench.com/assets/reports/vulcanbench-grok46-grokbuild-report.pdf).
- **Scale of a real long run**: one user's Grok 4.5/Grok Build run (1h08m) logged ~**363 tool calls, 100 files, ~620k tokens** reported, on a $30 SuperGrok plan (~$20 est. at API rates); but Grok Build "did not provide the same breakdown" as Claude Code's cache-write/read split, making cross-tool token comparisons messy — [Kodus comparison (2026-08-15)](https://kodus.io/en/grok-vs-opus/).
- **Community implementations (not xAI-affiliated)**:
  - **superagent-ai/grok-cli** (3.5k stars, MIT, TypeScript/Bun, "not affiliated with or sponsored by xAI"): sub-agents on by default (foreground `task`, background read-only `delegate`), `search_x`/`search_web` tools, media generation, computer sub-agent, Telegram remote control, headless `--max-tool-rounds`, `--batch-api` for cheap unattended runs — [github.com/superagent-ai/grok-cli](https://github.com/superagent-ai/grok-cli). No dedicated summarization/compaction mechanism was found in public documentation (gap below).
  - Forks of the official OSS tree: **SurmountSystems/grok-oss** (unofficial fork, adds OpenRouter option), **mweinbach/open-grok** ("Grok Build with ChatGPT Codex optimizations"), **DaviRain-Su/hyper-grok-build** (multi-provider), **mahdi-salmanzade/GrokForge** (Rust, MIT; notable feature: a **"context ledger"** accounting every request body's source bytes and redactions, subagents in isolated worktrees) — respective GitHub READMEs.
  - Grok Build's config is extensible to **any model via `~/.grok/config.toml`** (`[model.my-model]` with `base_url`), i.e., the harness can run against non-Grok providers including local inference — [docs.x.ai/build/overview](https://docs.x.ai/build/overview).

### Inferences
- Grok Build's philosophy is closest to Claude Code's among major harnesses (auto-compaction on usage %, structured handoff summaries, slash-command observability), with two xAI-specific twists: the server-side `/v1/responses/compact` encrypted-item API does the summarization on the provider side (its economics and failure modes analyzed in xAI's own cookbook), and models themselves expose selectable context-window sizes.
- The absence of tool-output folding at ingest (hooks are allow/deny only) is the clearest structural difference from harnesses like Claude Code's or agents that truncate tool results; xAI instead leans on earlier compaction + cheap cached re-sends.

### Gaps
- Exact internal structure/point-size of Grok Build's default system prompt is in the open-source repo but was not quantified here (the Terry Li experiment implies a minimal override barely dents the bill, so the base prompt is not the dominant cost).
- superagent-ai/grok-cli's own compaction strategy (if any) not documented publicly; its README does not surface one.

## Key Question 5: xAI's public efficiency posture — claims, benchmarks, cost-per-task, cache-price comparison

### Takeaway
xAI's marketing spine across 2025–2026 is **"intelligence density"**: more useful work per output token at fast serve rates. Verified form: Grok 4 Fast's "40% fewer thinking tokens" claim (2025), Grok 4.5's "4.2× fewer output tokens per SWE-Bench Pro task than Opus 4.8" (15,954 vs 67,020), Grok 4.7's "frontier price-performance on CursorBench 4.0," and price action ($2/$6 flagship). Independent corroboration is partial: Artificial Analysis independently measures ~14k output tokens per Intelligence Index task and ~$0.31/task for Grok 4.5 in Grok Build — consistent with the direction of the claim — but its vendor-harness methodology is contested by a third-party token-bill audit showing a thin harness can beat xAI's own harness by 16× total tokens on micro-tasks.

### Cited Findings
- **Grok 4 Fast (2025-09-19)**: RL-trained for "intelligence density," "achieves comparable performance to Grok 4 on benchmarks while using **40% fewer thinking tokens** on average"; combined with price → "**98% reduction in price to achieve the same performance** on frontier benchmarks"; independently verified by Artificial Analysis as SOTA price-to-intelligence — [x.ai/news/grok-4-fast](https://x.ai/news/grok-4-fast).
- **Grok 4.5 (2026-07-16)**: "solves tasks in under half the number of steps," "roughly **2× the token efficiency** of comparable leading models," 80 TPS; benchmark exercise: **15,954 avg output tokens per SWE Bench Pro task vs 67,020 for Opus 4.8 (4.2× fewer)**; default in Grok Build — [x.ai/news/grok-4-5](https://x.ai/news/grok-4-5).
- **Independent check of Grok 4.5**: Artificial Analysis Coding Index score 76 (≈ GPT-5.5 in Codex), **~14,000 output tokens per task, >60% fewer than Opus 4.8, ~$0.31 per task** — direction-aligned with xAI's claim (with xAI's higher numbers for SWE-Bench Pro) — [kingy.ai (2026-07-08)](https://kingy.ai/blog/grok-4-5-benchmarks-pricing-context-window/).
- **Grok 4.7 (2026-09-21)**: "twice as fast, at half the price of comparable models"; "better at verifying its own work and **managing longer context**"; frontier in price-performance on CursorBench 4.0 (stresses long-running tasks); 46.3% at xhigh effort there — [x.ai/news/grok-4-7](https://x.ai/news/grok-4-7), [cursor.com/grok](https://cursor.com/grok).
- **Agent-tools benchmark framing (Grok 4.1 Fast)**: xAI measured cost alongside accuracy on agentic-search tasks (e.g., X Browse avg. cost $0.091) explicitly positioning "fast + cheap tool calling" — [x.ai/news/grok-4-1-fast](https://x.ai/news/grok-4-1-fast).
- **Cache price vs Anthropic/OpenAI**: Grok's fully automatic 0.25× hit pricing is shallower per token than Anthropic (0.1× cached read, no Anthropic write-premium is 1.25× on write) but cheaper to invoke (no markers, no write premium) — compared directly by the APIYI analysis ("vs Claude: no cache_control markers — it just happens"; "vs OpenAI: equally automatic and free to write") — [docs.apiyi.com/en/api-capabilities/grok/prompt-caching](https://docs.apiyi.com/en/api-capabilities/grok/prompt-caching). On the *agentic coding* line specifically, `grok-build-0.1`'s $0.20/1M cached price is roughly the sector floor (grok-code-fast-1's cited $0.02/1M superseded it with lower absolute input price).
- **Engineering-blog-level treatment of harness token usage**: xAI's own docs are unusually explicit about harness-agnostic mechanics — the cookbook's "what breaks caching," "compaction cost more than it saved" and 128-token-block findings are published engineering detail rather than marketing ([docs.x.ai cookbook](https://docs.x.ai/cookbook/examples/prompt-caching), [Context Compaction guide](https://docs.x.ai/developers/advanced-api-usage/context-compaction)).
- **Third-party skepticism**: Terry Li's study shows the same quality at 16× the tokens between a bare API loop and Grok Build on micro-tasks, and argues "a pass rate belongs to the model, prompt, harness, tools, and verifier together," warning that efficiency comparisons must split input/cache-read/output/reasoning ([terryli.ai, 2026-08-24](https://terryli.ai/posts/the-harness-is-part-of-the-token-bill/)). VulcanBench in turn shows that inside xAI's own harness the *effort knob finally does what it promises* (monotone accuracy with tripled token spend at xhigh) — i.e., the harness earns its bill on long-horizon tasks rather than micro ones ([VulcanBench](https://vulcanbench.com/assets/reports/vulcanbench-grok46-grokbuild-report.pdf)).
- **Team/enterprise commercial framing**: Grok Bot is billed as a seat/plan product ($200 individual / $120-seat Teams via Cursor), not per-token; Bots carry "their own usage separate from your Grok or Cursor plans" — [x.ai/news/grok-bot-more-plans](https://x.ai/news/grok-bot-more-plans), [VentureBeat](https://venturebeat.com/orchestration/spacexais-grok-bot-turns-agents-into-persistent-digital-coworkers-that-can-operate-your-apps-for-120-per-month).
- **xAI has no official engineering blog post specifically on "agentic token usage"** beyond the cookbook/prompt-caching docs and Context Compaction guide; the open-sourced Grok Build harness doubles as the canonical "documentation" of the harness approach ("read the source to see exactly how it works, from context assembly to tool-call dispatch") — [x.ai/news/grok-build-open-source](https://x.ai/news/grok-build-open-source).

### Inferences
- For a comparison against Flynncode: xAI's stack optimizes the token bill primarily through **(1) server-side encrypted reasoning replay, (2) automatic prefix caching with 128-token blocks, (3) server-side context compaction API, (4) cheap coding-specialized model (grok-build-0.1) at ~10–16% of flagship price, (5) reasoning-effort throttles, and (6) cheap Batch/off-peak paths** — while consciously *not* investing in harness-level tool-output folding, which its docs show is the fix for the dominant residual cost; compaction and caching order respects matters (compaction items must come first; compaction drops anything before it, including `instructions`).
- The vendor's price-performance claims are partially independently corroborated (output token efficiency direction) but total-token comparisons of its harness against thin loops show the harness itself is a major cost multiplier; subscription-bundled access (Grok Build within SuperGrok/Cursor, Grok 4.7 Fast plan-billed) removes marginal-cost visibility — as also seen in the VulcanBench/Grok Build billing label discrepancy (`grok-4.6` requested, `grok-4.6-build` served).

### Gaps
- No official cost-per-task or cost-per-PR numbers from xAI for Grok Build; all cost-per-task figures found are third-party benchmarks or estimated by users.
- Any official comparison table of cache/TTL vs Anthropic/OpenAI at the docs level was not located (only third-party comparisons, cited above).
