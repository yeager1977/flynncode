# Copy supervision loops, skip vendor clouds
Flynncode already owns the session shell both vendors spent 2026 converging on — review pane, file tree, PTY terminal, worktrees, permissions, plugins/MCP/skills, Ollama router, routines, dispatch, artifacts — but it lacks the return path that makes supervision work: disposable per-chat worktrees with handoff, last-turn scoped review with hunk actions and an "address comments" follow-up, and one activity inbox for running/needs-input/blocked runs. Claude runs one engine across CLI, IDE, Desktop Code tab, web cloud VMs, and mobile thin clients with deny>ask>allow permissions and Manual/AcceptEdits/Plan/Auto/Bypass modes ([Source](https://code.claude.com/docs/en/overview.md)) ([Source](https://code.claude.com/docs/en/permissions.md)) ([Source](https://code.claude.com/docs/en/desktop.md)), while Codex runs local-first in CLI/IDE/desktop with Seatbelt/bubblewrap/Windows-sandbox enforcement plus reusable cloud environments per task and QR-paired mobile remote control ([Source](https://developers.openai.com/codex/sandboxing)) ([Source](https://developers.openai.com/codex/environments/cloud-environments)) ([Source](https://developers.openai.com/codex/mobile)). The October 2026 cutover that moves Claude Cowork off "Only on your computer" onto Anthropic servers ([Source](https://claude.com/product/cowork)) and Codex's cleaner split where local tasks die asleep and cloud tasks cannot see local files ([Source](https://developers.openai.com/codex/automations)) both argue for Flynncode's opposite trade: keep inference and workspace on user-controlled machines, target sleep-surviving work at the user's deepthought host at 192.168.4.251 instead of any vendor cloud, and protect the Ollama model router's offline-local advantage while copying only local-reach and supervision traits.

## Claude runs one engine across five placements with host-enforced permissions
Claude Code is an agentic coding tool available in terminal, IDE, desktop app, and browser that reads codebases, edits files, runs commands, and integrates with dev tools, and each surface connects to the same underlying engine so repo CLAUDE.md, settings, and MCP servers work across them ([Source](https://code.claude.com/docs/en/overview.md)). The CLI is the most complete surface for terminal-native work since scripting and Agent SDK are CLI-only, while the desktop trades CLI-only features for visual review and tighter editor integration, web runs in cloud so tasks keep going after disconnect, and mobile is a thin client into cloud sessions or local sessions via Remote Control ([Source](https://code.claude.com/docs/en/platforms.md)). The desktop app has three tabs — Chat for conversations, Cowork for Dispatch and longer agentic work, Code for software development — and in the Code tab each conversation is a session with its own history and project folder where Environment (Local/Cloud/SSH/WSL), Project folder, Model, and Permission mode are configured before the first message ([Source](https://code.claude.com/docs/en/desktop.md)). Desktop Code features include a diff viewer with inline comments, an app preview Browser pane with auto-verify, an iOS Simulator pane, drag-and-drop panes, integrated terminal and file editor, side chats, computer use, Dispatch, PR monitoring, and connectors ([Source](https://code.claude.com/docs/en/desktop.md)). Cowork is built for non-coding knowledge work using the same agentic approach as Claude Code while Code is built for writing/debugging/shipping code, and in regular chat Claude responds without direct file access whereas in Cowork it has permission to read/edit/create files in specified folders ([Source](https://claude.com/product/cowork)). Cowork runs on desktop with web and mobile in beta, and the desktop adds folders and applications on the user's own computer ([Source](https://claude.com/product/cowork)).

Execution splits cleanly. A cloud session runs on cloud infrastructure instead of the user's machine, by default Anthropic-managed or org self-hosted when routed there, and keeps running after the laptop closes, with each session isolated via VMs, network access controls, and credential protection where git creds stay outside the sandbox and a proxy authenticates with scoped creds ([Source](https://code.claude.com/docs/en/claude-code-on-the-web.md)). Cloud environments control network access, env vars, and setup scripts, the Default environment uses Trusted access allowing only a default allowlist of registries and cloud APIs, connectors reach services via Anthropic servers without allowlist changes, and setup script results are cached ([Source](https://code.claude.com/docs/en/routines.md)). GitHub access goes via the Claude GitHub App or /web-setup sending a local gh token, with creds encrypted and never entering Anthropic-hosted VMs ([Source](https://code.claude.com/docs/en/claude-code-on-the-web.md)). Permissions are tiered: read-only tools need no approval in working dirs, Bash and file modification ask, WebFetch/WebSearch mostly allowed, prompts offer Yes/Yes-don't-ask-again/Yes-switch-to-auto/No with file-mod approval lasting until session end, and rules evaluate deny then ask then allow ([Source](https://code.claude.com/docs/en/permissions.md)). Modes are default/Manual, acceptEdits, plan, auto classifier, dontAsk (CLI-only), and bypassPermissions which only belongs in isolated containers and can be disabled ([Source](https://code.claude.com/docs/en/permissions.md)). Bash rules match whole command text with `*` family coverage and compound `&&/||/;/|/|&` requiring each subcommand to match, read deny also blocks Edit/Write on the same path, and in Cowork Claude runs shell via mcp__workspace__bash so whole-tool Bash/WebFetch deny applies but allow does not carry over ([Source](https://code.claude.com/docs/en/permissions.md)). Desktop exposes Manual, Accept edits, Plan, Auto, and Bypass (Pro/Max toggle, org policy on Team/Enterprise) while cloud supports Accept edits, Plan, and Auto with no Bypass, and Routines run autonomously as full cloud sessions with no permission-mode picker ([Source](https://code.claude.com/docs/en/desktop.md)) ([Source](https://code.claude.com/docs/en/routines.md)).

Integration follows three primitives. MCP is the USB-C integration layer with Connectors UI plus .mcp.json plus per-subagent servers plus org allowlists, subagents are markdown-defined workers with isolated context that return summaries, and Routines plus Desktop tasks plus /loop cover cloud, local, and in-session scheduling ([Source](https://modelcontextprotocol.io/)) ([Source](https://code.claude.com/docs/en/sub-agents.md)) ([Source](https://code.claude.com/docs/en/routines.md)) ([Source](https://code.claude.com/docs/en/overview.md)). Subagent files use Markdown YAML frontmatter with required name/description and optional tools/model/permissionMode/skills/mcpServers/effort/isolation, scope priority runs Managed > CLI flags > project > user > plugin, and isolation:worktree runs a subagent in a temp git worktree branched from the default branch ([Source](https://code.claude.com/docs/en/sub-agents.md)). Routines are saved prompt+repos+connectors running on Anthropic cloud or self-hosted infra with Scheduled/API/GitHub triggers, created at claude.ai/code/routines or /schedule ([Source](https://code.claude.com/docs/en/routines.md)). Cross-device steering uses Dispatch (phone to Desktop machine), Remote Control (drive a running session from web/mobile via claude remote-control), Channels and Slack @Claude, self-hosted runners, and CLI --cloud/--teleport where --cloud clones the GitHub remote at the current branch and --teleport pulls a cloud branch plus history into the terminal one-way ([Source](https://code.claude.com/docs/en/platforms.md)) ([Source](https://code.claude.com/docs/en/claude-code-on-the-web.md)). The browser story splits: the Desktop Browser pane is a clean profile separate from personal logins while the Chrome extension shares login state for acting as the user, and Cowork's built-in browser is a side panel separate from the user's own browser requiring per-session sign-in or cookie import ([Source](https://code.claude.com/docs/en/desktop.md)) ([Source](https://claude.com/product/cowork)). Computer use tries connector then Bash then Chrome then iOS Simulator then screen control, with per-app Allow per session or 30-minute Dispatch grants ([Source](https://code.claude.com/docs/en/desktop.md)). From April to October 2026 Anthropic shipped cloud Sessions/Projects/Routines, auto mode default, agent teams with messaging, Desktop Linux/iOS/computer-use background, Chrome GA, and Sonnet/Opus/Fable 5.x becoming defaults plus Haiku/Sonnet/Opus 5.5 cost/speed wins, with week 32 making auto mode default and week 34 enabling starting a machine session from a phone ([Source](https://code.claude.com/docs/llms.txt)).

## Codex stays local-first and delegates long work to published cloud environments

The IDE extension brings open files, selection, and recent chats into the prompt with inline diff review and delegation to cloud, sharing config.toml and MCP config with the CLI ([Source](https://developers.openai.com/codex/ide)). Codex Cloud uses reusable published environments — repos plus deps plus tools plus network/secrets — where each task gets an isolated workspace/VM started from web/desktop Work in > Cloud or mobile Codex or `codex cloud` from CLI or Slack/Teams @ChatGPT or GitHub @codex, running while the computer sleeps ([Source](https://developers.openai.com/codex/cloud)) ([Source](https://developers.openai.com/codex/environments/cloud-environments)). Since 2026-07-09 Codex has been merged into the ChatGPT desktop app with a dedicated Codex view alongside Chat/Work, supporting local projects, multi-folder, review pane, browser/computer use, scheduled tasks, pets/appshots, and voice ([Source](https://developers.openai.com/codex/changelog)). Mobile has no local execution and instead starts, guides, and reviews Cloud tasks or remote tasks on a connected Mac/Windows PC with QR pairing, worktrees, widgets, and task search ([Source](https://developers.openai.com/codex/mobile)). The CLI, app-server, and SDK components are open source in openai/codex under Apache-2.0 ([Source](https://github.com/openai/codex).

Local execution is sandboxed per OS: Seatbelt on macOS, bubblewrap on Linux/WSL2, Windows Sandbox, with read-only, workspace-write default, and danger-full-access levels, and spawned commands including git and test runners inherit those boundaries ([Source](https://developers.openai.com/codex/sandboxing)). Approvals default to on-request with a never option, `writable_roots` extends writable dirs without removing the sandbox, `rules` allow/prompt/forbid command prefixes, and auto-review via a reviewer agent approves or denies eligible boundary crossings without expanding the sandbox ([Source](https://developers.openai.com/codex/sandboxing)). Full access equals danger-full-access plus never asking and stays hidden until Settings enables it, which is the permission split to copy ([Source](https://developers.openai.com/codex/permission-modes)). Non-interactive `codex exec "<prompt>"` streams progress to stderr and the final message to stdout with --json JSONL events, structured --output-schema output, --ephemeral rollout skipping, resume by session ID for two-stage pipelines, and a CI pattern using openai/codex-action with split generate_fix and open_pr jobs ([Source](https://developers.openai.com/codex/non-interactive-mode)). Local `/review` offers base-branch, uncommitted, and commit presets with a dedicated reviewer that never mutates the working tree and an optional separate review_model ([Source](https://developers.openai.com/codex/code-review)).

Cloud environments are created on web or desktop via Work in > Cloud, picking GitHub repos, letting Codex inspect and install deps, supplying missing access, then Save and Publish so new tasks start from the published filesystem while existing tasks keep their own state ([Source](https://developers.openai.com/codex/environments/cloud-environments)). Env config covers install script plus Start skill, direct environment variables versus placeholder Network secrets proxied for allowed HTTPS:443 domains, per-user Personal vault, Allow-internet presets for package managers or Custom/Unrestricted, Tailscale VPN, and Enterprise OIDC, with VM sizes at 2vCPU/8GB for Plus and 4vCPU/16GB/32GB for Pro/Business/Enterprise and saved VMs recoverable 7 days ([Source](https://developers.openai.com/codex/environments/cloud-environments)). Desktop specifics include multi-folder local projects since 26.715, a review pane scoping Unstaged/Staged/Commit/Branch/Last turn with per-diff/file/hunk stage/unstage/revert and inline `+` comments, PR Chat, Sites, an artifacts viewer, integrated multi-terminal, tray, and multi-window support ([Source](https://developers.openai.com/codex/changelog)). The built-in browser is desktop-only on a separate profile with Annotate mode to click or drag a region, comment, optionally adjust font/text/spacing/color, and send into chat, with OpenAI telling users to prefer it over Computer Use for local web apps, while Computer Use on Windows takes the foreground and pointer and cannot drive terminals or the ChatGPT app itself ([Source](https://developers.openai.com/codex/browser)) ([Source](https://developers.openai.com/codex/computer-use)). Appshots capture screenshot plus available text via double-Command or double-Alt ([Source](https://developers.openai.com/codex/changelog)). GitHub code review connects a repo so @codex review posts P0/P1-only reviews with Automatic review triggers and @codex fix CI failures starting a legacy cloud chat that can push to the branch, customized via Code Review Rules in the nearest AGENTS.md, with Security Review as a deeper research-preview diff plus threat-model pass ([Source](https://developers.openai.com/codex/third-party/github)). GitLab @codex from issues and MRs entered beta 2026-08-19 ([Source](https://developers.openai.com/codex/changelog)). ## Flynncode owns the shell but the supervision return path is unfinished
On dev at c5dd8e0e43 dated 2026-10-08 the Electron shell around the web app already contains the surfaces both vendors use to look modern: SessionSidePanel with review and file tree, review v1 line comments and review v2 sidebar plus file tree plus preview plus diff kinds, PTY terminal panels, todo dock, subagent and task list, message timeline, composer docks for questions/permissions (once/always/reject)/follow-ups/reverts/todos, and v1/v2 layouts behind a settings flag. Git worktree create/list/remove/reset exists on the server with a "Create new worktree" entry in new-session view and a sandbox listing in the sidebar, hunk stage/unstage exists in the session page, plugins/MCP/skills settings plus desktop plugin manager plus MCP registry search exist, the Flynncode-specific Ollama model router loads by default and stays inert without a model_router key while exposing rank_models and route_task, and routines (30-second poll, manual plus dailyAt only), dispatch (local list capped at 40), artifacts sidebar (session_diff groups, max 20), unfocused-window notifications, servers/WSL pages, LAN mobile gateway on default port 4097, session share view links, and deep links are all on disk. What was not found is Codex's disposable per-chat retention with explicit checkout handoff, last-turn versus branch review scoping with a one-step "address these comments" follow-up, an Activity-style inbox with running/needs-input/blocked states spanning dispatch plus routines plus notifications, RRULE cadence plus run history, a built-in browser pane with element annotations beside the diff, a global quick-entry composer, on-disk opt-in memories with redaction, sandbox-versus-approval permission separation with an auto-approve reviewer, background subagent stop/steer from the list, and any computer-use surface beyond hosted protocol passthrough that the runtime does not execute. Voice, Sites with every-URL-production semantics, cloud agent loops, Computer History screen recording, vendor sign-in import, and pane pop-out are the items to explicitly skip under the local-first, no-vendor-cloud, Ollama-router constraints. New work should extend the existing review, worktree, dispatch, routines, notification, subagent-list, and server-attach surfaces rather than adding parallel panes, schedulers, or placement vocabularies.

## Prioritized build list ordered high to low
Each item states type (Feature = new capability, Fix = gap in something Flynncode claims to do), who has it, why it matters for Flynncode, and rough effort. Vendor-cloud items are adapted to local sidecar or user-owned deepthought host per constraints; skipped items are listed after the build list with reasons.

1. **Review return path: last-turn scope plus address-comments follow-up plus hunk stage/revert** — Type: Fix. Who: Codex (review pane scopes Unstaged/Staged/Commit/Branch/Last turn, inline `+` comments, stage/unstage/revert at diff/file/hunk, "Address the inline comments" follow-up ([Source](https://developers.openai.com/codex/code-review))). Why: Flynncode already renders diffs and line comments but cannot close the supervision loop without scoping to the last turn and turning comments into the next turn in one action. Effort: medium.
2. **Disposable per-chat worktrees with retention plus checkout handoff** — Type: Fix. Who: Codex (per-chat managed worktrees under $CODEX_HOME/worktrees, 15-most-recent retention, Handoff between Local and Worktree ([Source](https://developers.openai.com/codex/environments/git-worktrees))). Why: Flynncode creates and lists worktrees but leaves disposal and branch-moving to the user, which breaks parallel-agent supervision. Effort: medium.
3. **One activity inbox: running, needs input, blocked across dispatch plus routines plus sessions** — Type: Feature. Who: Codex (Activity bell with Work/Chat/Pinned/Scheduled filters, floating pets with Running/Needs input/Ready/Blocked ([Source](https://developers.openai.com/codex/notifications))); Claude (agent view managing all sessions). Why: Flynncode has three thin lists (dispatch, routines, notifications) and no single place a human watches supervised runs. Effort: medium.
4. **Permission hardening: separate sandbox from approvals plus auto-approve reviewer** — Type: Fix. Who: Codex (sandbox modes vs approval policy, Full access hidden until enabled, auto-review reviewer agent ([Source](https://developers.openai.com/codex/sandboxing))); Claude (deny>ask>allow, Manual/AcceptEdits/Plan/Auto/Bypass ([Source](https://code.claude.com/docs/en/permissions.md))). Why: Flynncode's permission dock exists but conflates isolation with consent, inviting accidental full-access defaults. Effort: medium.
5. **Built-in browser pane beside diff for local dev servers with annotate-to-chat** — Type: Feature. Who: Codex (desktop-only separate-profile browser, Annotate click/drag plus Adjust, prefer over Computer Use ([Source](https://developers.openai.com/codex/browser))); Claude (Code-tab Browser pane with dev-server start plus auto-verify screenshots/DOM/clicks ([Source](https://code.claude.com/docs/en/desktop.md))). Why: Previewing the running app next to the diff is the highest-leverage local-reach gap for a coding desktop. Effort: large.
6. **RRULE cadence plus run history for routines, targetable at desktop sidecar or deepthought** — Type: Fix. Who: Codex (standalone vs in-chat scheduled tasks, RRULE custom, worktree isolation ([Source](https://developers.openai.com/codex/automations))); Claude (Routines with Scheduled/API/GitHub triggers ([Source](https://code.claude.com/docs/en/routines.md))). 7. **Global quick-entry composer on the existing deep-link path** — Type: Feature. Who: Claude (macOS double-tap Option composer from any app with screenshot/window attach, Linux X11/Wayland portal ([Source](https://support.claude.com/en/articles/12626668-use-quick-entry-with-claude-desktop-on-mac))). Why: Capturing intent without context-switching is the cheapest way to feed the supervision loop from other apps. Effort: small.
8. **Local /review presets (base-branch, uncommitted, commit) with detached-chat option** — Type: Feature. Who: Codex (local /review presets, no tree mutation, detached delivery ([Source](https://developers.openai.com/codex/code-review))). Why: Gives reviewers a no-mutation read path distinct from the editable review pane, matching how teams actually gate merges. Effort: small.
9. **Background subagent stop and steer from the existing subagent list** — Type: Fix. Who: Claude (background subagents, subagent permission scoping ([Source](https://code.claude.com/docs/en/sub-agents.md))); Codex (background-agent panel above composer, subagent threads ([Source](https://developers.openai.com/codex/agent-configuration/subagents))). 11. **On-disk opt-in memories with secret redaction, never synced** — Type: Feature. 13. **Multi-folder local projects with a primary folder for Git/AGENTS discovery** — Type: Feature. Who: Codex (multi-folder since 26.715, primary folder for Git/AGENTS.md/config.toml discovery ([Source](https://developers.openai.com/codex/changelog))). 14. **Subagent isolation in temp worktrees plus per-agent model/sandbox overrides** — Type: Feature. Who: Claude (isolation:worktree, per-subagent model/permissionMode/tools ([Source](https://code.claude.com/docs/en/sub-agents.md))); Codex (custom agent .toml with model/reasoning/sandbox/MCP ([Source](https://developers.openai.com/codex/agent-configuration/subagents))). Who: Claude (beta Pro/Max, per-app prompts, background windows ([Source](https://code.claude.com/docs/en/desktop.md))); Codex (plugin, foreground-takes-pointer on Windows, cannot drive terminals ([Source](https://developers.openai.com/codex/computer-use))). Explicitly skipped under Flynncode constraints: vendor-hosted cloud sessions and cloud environment images (both vendors) — use deepthought host instead; Gmail/Slack/GitHub webhook event triggers (Codex web-only) — pulls third-party inboxes into a local desktop; Sites production hosting (Codex) and voice chat products (both) — cloud speech/hosting with residency conflicts; Computer History screen recording (Codex) — recorder with memory attached; Cowork-style knowledge-work home merged into chat (Claude) — Flynncode is a coding desktop and should not fork then re-merge; vendor sign-in import as a prerequisite for supervision — the Ollama router already gives offline-local turns neither vendor documents.

## Conclusion
The vendors converged on the same discovery: a coding desktop is a supervisor for parallel agents with isolated placements and a commentable diff as the return path, and then each attached a cloud that Flynncode must refuse. Flynncode's build order falls out directly: finish the loop first (worktree disposal plus handoff, last-turn review plus address-comments, activity inbox, permission split), then reach (browser pane, quick entry, memories, multi-folder), then the awake half on hardware the user owns (RRULE routines plus deepthought targeting, phone needs-input relay), with computer use only after the browser proves out. That sequence protects the one advantage neither vendor claims — local-model turns through the Ollama router with the network down — while copying exactly the supervision traits their own reviews praise.
