# Copy supervision traits, skip their cloud

As of 30 September 2026, the desktop trait worth copying is a supervision loop, not a model and not a hosted agent. OpenAI's Codex surface, now a mode inside the ChatGPT desktop app, keeps many chats visible, gives each chat a place to run, and returns finished work to one diff the user can comment on, stage, and revert without leaving the app. Anthropic's Claude Desktop is the better local-reach shell — dock quick entry, folders, extensions, a built-in browser, computer use, and Code-tab panes — but new Cowork tasks for Pro and Max move onto Anthropic's servers on 6 October 2026, and "Only on your computer" is removed. Flynncode should copy the missing return path of that loop and the local-reach pieces it does not already have, and it should refuse both vendors' clouds. The fork already has review, Git worktree creation, a PTY terminal, a file tree, permission docks, a plugin manager, MCP settings, an Ollama model router, local routines, an artifacts sidebar, a dispatch list, unfocused-window notifications, and a same-LAN mobile gateway. Rebuilding those is the design failure. Work that must stay awake when the laptop sleeps belongs on the user's deepthought host, microk8s at 192.168.4.251, not on a public control plane.

## Parallel chats and a commentable diff are the trait reviews praise

OpenAI launched the Codex app on 2 February 2026 as a desktop for parallel agent threads, with a project sidebar, a thread list, worktrees, and a review pane, because IDEs and terminals are not built for supervising many long-running agents ([Introducing the Codex app](https://openai.com/index/introducing-the-codex-app/)). On 9 July 2026 that app became a mode inside the ChatGPT desktop app; existing projects and settings carry over, and Codex can stay the default view ([Changelog, 2026-07-09](https://developers.openai.com/codex/changelog)). The current composer still chooses ChatGPT or Codex, and Quick chat is a separate ChatGPT thread that does not appear in the Codex sidebar ([ChatGPT desktop app](https://developers.openai.com/codex/app/); [Projects and chats](https://developers.openai.com/codex/projects)). Treat "threads" in the February launch notes and "chats" in the September docs as the same object.

The structural difference is placement. A new Codex chat runs on **this computer**, in a **worktree**, or in the **cloud** ([Codex environments](https://developers.openai.com/codex/environments/modes)). Worktree creates a Git worktree, detached HEAD by default, under `$CODEX_HOME/worktrees`, from main, a feature branch, or the current branch including unstaged changes. **Handoff** moves that chat and its code between the local checkout and the worktree; Git still allows a branch in only one worktree, and ignored files move only if `.worktreeinclude` says so ([Worktrees](https://developers.openai.com/codex/environments/git-worktrees)). Managed worktrees are per-chat and disposable, with a default retention of the **15 most recent**, and they are not deleted while a pinned or in-progress chat is tied to them. Permanent worktrees are their own project and can host several chats. Non-Git folders cannot use worktrees at all.

The return path is the review pane, and it is not the same thing as the Code Review plugin. The pane scopes **Unstaged, Staged, Commit, Branch, and Last turn**, takes inline comments, and stages, unstages, or reverts at diff, file, or hunk. `/review` leaves findings as inline comments and does not change the working tree. A follow-up such as "Address the inline comments" is the documented way those comments re-enter the chat ([Code review](https://developers.openai.com/codex/code-review)). The pinnable Code Review plugin is a GitHub pull-request inbox, generally available, with GitLab merge requests in preview; posting a review is a separate submit step. Copy the local pane. Do not build a hosted pull-request product to get the trait.

Reviews that describe what the author actually did agree on that loop and disagree on almost everything else. A 27 February 2026 hands-on, three weeks of daily macOS use, rated the app 7.8/10 and named three agents in separate worktrees, diff review with line comments and hunk revert, and automations landing in a review queue as the best observed behavior ([Awesome Agents review](https://awesomeagents.ai/reviews/review-openai-codex-app/)). A review updated 17 June 2026 calls worktrees the structural difference versus single-branch CLI use ([vibecoding.app review](https://vibecoding.app/blog/openai-codex-app-review)). A how-to updated 30 September 2026 still treats automations plus the review queue as the power features, and its worktree mechanics match the official page ([Daniel Vaughan](https://codex.danielvaughan.com/2026/04/08/codex-desktop-automations/)). That February review's claim that every app agent runs in a cloud container is contradicted by the launch post and by the current Local and Worktree docs. Its macOS-only complaint is also stale: OpenAI's own post notes Windows availability on 4 March 2026. No independent review dated after the 9 July merge was found that re-tests worktrees, review, computer use, and voice together ([DuckDuckGo query](https://html.duckduckgo.com/html/?q=Codex+desktop+app+review+2026+worktrees+diff)). The praised core is still the supervision loop. The untested part is whether Pets, voice, and Sites diluted it after the merge.

"Runs locally" in this product means the workspace, sandbox, terminal, browser, and computer-use tools are on the machine. It does not mean the model is local. Setup requires a ChatGPT sign-in, and a cloud task does not receive the computer's files, processes, browser sign-ins, or VPN ([ChatGPT desktop app](https://developers.openai.com/codex/app/); [Codex environments](https://developers.openai.com/codex/environments/modes)). Sandbox enforcement is local: Seatbelt on macOS, the Windows sandbox, bubblewrap on Linux ([Sandbox](https://developers.openai.com/codex/sandboxing)). Approval is separate from the sandbox. **Approve for me** does not widen it; **Full access** is `danger-full-access` plus never asking, and it stays hidden until Settings turns it on ([Permissions](https://developers.openai.com/codex/permission-modes)). That split is the permission trait to copy. The ChatGPT account is not.

## Claude's local reach is real, and Cowork is leaving it

Anthropic's own desktop pitch is continuity: dock access, quick entry from any app, and desktop extensions for local files, against a terminal that cannot show parallel sessions and side-by-side panes ([Download Claude](https://claude.com/download); [Desktop application](https://code.claude.com/docs/en/desktop)). On 16 September 2026 they merged Cowork into chat so the user stops deciding whether a message is a question or a task ([Cowork is now Claude](https://claude.com/blog/cowork-is-now-claude)). That merge is a product lesson, not a feature to clone. Flynncode is a coding desktop. It should not grow a second home for "knowledge work" and then spend a year gluing the two back together.

The local-reach pieces that are still distinctive, and still missing or thin in a coding shell, are four. **Quick entry** on macOS opens a composer from any app, can attach a screenshot or another window, and is also a Linux hotkey on X11 or via the Wayland GlobalShortcuts portal; the dedicated article still says it is not on Windows ([Quick entry](https://support.claude.com/en/articles/12626668-use-quick-entry-with-claude-desktop-on-mac); [Install Claude Desktop](https://support.claude.com/en/articles/10065433-install-claude-desktop)). **Desktop extensions** are local MCP packages, with secrets in the OS keychain, and they are the reason the desktop app is not just the website ([Local MCP servers](https://support.claude.com/en/articles/10949351-getting-started-with-local-mcp-servers-on-claude-desktop)). **A built-in browser** in a side panel, rolling out the week of this research for Cowork on macOS, Windows, and Linux beta, clicks and fills forms; cookie import leaves banking, email, and SSO unchecked by default, and sign-ins persist on that computer ([Built-in browser](https://support.claude.com/en/articles/16607400-use-the-built-in-browser-in-claude-cowork)). The Code tab's browser is the closer analogue for Flynncode: Claude can start a dev server, open it beside the diff, and check it with screenshots, DOM, clicks, and forms; panes can pop out from v1.2581.0 ([Desktop application](https://code.claude.com/docs/en/desktop)). **Computer use** is beta, Pro and Max only, not on Linux, off until enabled, and explicitly worse than connectors: it screenshots permitted apps, has no sandbox, and on macOS 15+ defaults to background windows so the user keeps the pointer ([Computer use](https://support.claude.com/en/articles/14128542-let-claude-use-your-computer-in-cowork)).

Codex documents the same two tools with a sharper preference. Its built-in browser is desktop-only, uses a separate profile, and supports **Annotate**: click an element or drag a region, comment, optionally adjust font, text, spacing, or color, then send that into the chat. OpenAI tells users to prefer that browser over Computer Use for local web apps. Computer Use cannot drive a terminal or the ChatGPT app itself, and on Windows it takes the foreground and the pointer ([Browser](https://developers.openai.com/codex/browser); [Computer Use](https://developers.openai.com/codex/computer-use)). Copy the browser-first order and the annotation gesture. Do not copy a default that seizes the desktop, and do not copy Claude's sandbox-less screenshot path.

The cloud direction is the warning, not the roadmap. On 30 September 2026 the Cowork get-started page says tasks run in the cloud, sessions save to the Claude account, and the laptop can close; local files, the built-in browser, and computer use still need Desktop open as a broker ([Get started with Claude Cowork](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork)). The architecture page says the agent loop and code execution are on Anthropic servers by default, connector tokens never enter the sandbox, and files opened through Desktop are processed on Anthropic's servers ([Cowork architecture](https://support.claude.com/en/articles/14479288-claude-cowork-architecture-overview)). For Pro and Max, **6 October 2026** removes "Only on your computer." Tasks already started locally stay there. The surfaces article's advice, if you want work to stay on one machine, is to use Claude Code in the desktop app, and projects and scheduled tasks do not carry over ([Cowork on web, desktop, and mobile](https://support.claude.com/en/articles/15520349-use-claude-cowork-on-web-desktop-and-mobile)). The same week's install page still describes an on-computer VM, and Linux setup still requires KVM and QEMU ([Install Claude Desktop](https://support.claude.com/en/articles/10065433-install-claude-desktop)). Both descriptions are current and unresolved. No fetched page says model weights run on the device. Scheduled tasks are in the same muddle: the article says they run remotely even if the computer is asleep and cannot be tied to a local folder, and also says a task that needs local files or apps runs only locally ([Scheduled tasks](https://support.claude.com/en/articles/13854387-schedule-recurring-tasks-in-claude-cowork)). Codex is cleaner and less magical. Desktop scheduled tasks that need local files require the computer on and the app running; event triggers for Gmail, Slack, and GitHub are web and mobile only and are not in the desktop app ([Scheduled tasks](https://developers.openai.com/codex/automations)). Launch-day automations already landed in a review queue, which is the part worth copying; the cloud triggers OpenAI said were still being built are the part to leave ([Introducing the Codex app](https://openai.com/index/introducing-the-codex-app/)).

Voice, Sites, synced memory, and Computer History fail the local-first test. ChatGPT Voice is a cloud speech product, one voice chat at a time, Plus and above ([ChatGPT Voice](https://developers.openai.com/codex/features/voice)). Claude voice mode likewise sends the conversation to Claude and is "built to work best from your phone" ([Voice mode](https://support.claude.com/en/articles/11101966-use-voice-mode)). Sites publishes every deployment URL as production and does not support data residency ([Sites](https://developers.openai.com/codex/sites)). Claude memory syncs across phone, desktop, and web, and cloud Cowork shares it ([Download Claude](https://claude.com/download)). Codex local memories are the acceptable shape: off by default, files under `~/.codex/memories/`, secret redaction, generation skipped on short sessions and when rate limit is low ([Memories](https://developers.openai.com/codex/customization/memories)). Computer History, which turns activity in allowed apps into a timeline, is a screen recorder with a memory feature attached. Leave it off the list. Dictation that becomes prompt text is optional later, and only if speech never leaves the machine.

## The session shell is already built

Flynncode is an Electron shell around the app. The session page already owns the surfaces both vendors use to look modern. `SessionSidePanel` shows review and the file tree. Review v1 mounts the shared session-review component and emits line comments; review v2 adds a sidebar, file tree, preview, and diff kinds. A PTY terminal accepts keystrokes. A todo dock, a subagent and task list, a message timeline, and composer docks for questions, permissions (`once`, `always`, `reject`), follow-ups, reverts, and todos are all in `packages/app` ([session-side-panel.tsx](file:///home/yeager1977/GitHub/flynncode/packages/app/src/pages/session/session-side-panel.tsx); [review-tab.tsx](file:///home/yeager1977/GitHub/flynncode/packages/app/src/pages/session/review-tab.tsx); [session-composer-region.tsx](file:///home/yeager1977/GitHub/flynncode/packages/app/src/pages/session/composer/session-composer-region.tsx)). v1 and v2 sit behind `settings.general.newLayoutDesigns()`. New work picks that flag. It does not add a third panel.

Git worktrees are not a greenfield feature. The server exposes create, list, remove, and reset. The new-session view offers "Create new worktree," and the sidebar distinguishes a local workspace from a sandbox ([session-new-view.tsx](file:///home/yeager1977/GitHub/flynncode/packages/app/src/components/session/session-new-view.tsx); [layout.tsx](file:///home/yeager1977/GitHub/flynncode/packages/app/src/pages/layout.tsx)). What was not found is Codex's disposable per-chat retention and a **checkout handoff**. The file named handoff in the session page moves a prompt and selected lines between UI surfaces. It does not move a branch between the primary checkout and a worktree ([handoff.ts](file:///home/yeager1977/GitHub/flynncode/packages/app/src/pages/session/handoff.ts)). Line comments already enter composer context through `addCommentToContext` ([session.tsx](file:///home/yeager1977/GitHub/flynncode/packages/app/src/pages/session.tsx)). The missing supervision action is the Codex one: scopes for last turn versus the branch, hunk stage and revert, and one follow-up that means "address these comments." Message-level revert already has its own dock. Do not replace it with a Git hunk revert that pretends to be the same operation.

Plugins, skills, MCP, and routing are also occupied. A desktop plugin manager edits global and project config. MCP settings cover local and remote servers plus registry search. Skills load from directories, URLs, and embedded sources and appear in the slash popover; there is no skills settings page, and one is not the trait. The Ollama model router is Flynncode-specific, loads by default, stays inert without a `model_router` key, and exposes `rank_models` and `route_task` ([ollama-model-router](file:///home/yeager1977/GitHub/flynncode/packages/opencode/src/plugin/ollama-model-router/index.ts)). That router is why Flynncode can mean "local" in a stricter sense than either vendor. Do not add a ChatGPT or Claude sign-in as the price of the supervision loop. Third-party plugins still have to be checked against the router.

Routines, artifacts, dispatch, and notifications are early versions of the inbox, not empty slots. Routines poll every 30 seconds, support manual runs and `{ dailyAt: "HH:MM" }` only, and start a new session with the build agent on the server that loaded the plugin. The spec excludes full cron, webhooks, and run history beyond last-run ([routines/index.ts](file:///home/yeager1977/GitHub/flynncode/packages/opencode/src/plugin/routines/index.ts)). The artifacts sidebar groups `session_diff` files, at most 20 groups, and links back to the session. Dispatch is a local task list capped at 40. OS notifications fire only when the window is unfocused ([notification.tsx](file:///home/yeager1977/GitHub/flynncode/packages/app/src/context/notification.tsx)). Codex's Activity view — unread, running, waiting, with a bell — is the behavior to add to those surfaces, not a fourth list ([Notifications](https://developers.openai.com/codex/notifications)). Subagent threads are already listed, and same-server session messaging can steer another session. Extend that list so a running child can be stopped or steered. Do not invent a subagent pane.

The desktop already speaks to more than one machine, in a local shape. It spawns a sidecar server and can attach to remote HTTP servers and WSL sidecars. Settings already has a servers page ([servers.tsx](file:///home/yeager1977/GitHub/flynncode/packages/app/src/components/settings-v2/servers.tsx)). `@flynncode/mobile-gateway` is a LAN reverse proxy, default port 4097, so a phone on the same network can open the existing web app. The design notes that iOS will not deliver Web Push over plain LAN HTTP ([mobile-gateway README](file:///home/yeager1977/GitHub/flynncode/packages/mobile-gateway/README.md)). Session share is a view link, not a multi-user review room. Deep links already arrive in the desktop main process. No desktop computer-use surface exists; the only hits are protocol passthrough for a hosted `computer_use_call`, which the runtime does not execute ([openai-responses.ts](file:///home/yeager1977/GitHub/flynncode/packages/llm/src/protocols/openai-responses.ts)). No built-in browser pane and no global quick-entry composer were found in the desktop main process. Cross-device memory was not found. Persistence is scoped per server.

| Local file memories, off by default | No | Add on disk. Do not sync them to a vendor. |
| Voice, Sites, cloud Cowork, Computer History, event-trigger inbox | No | Skip. |

## Host the awake half on deepthought, then stop

The features that need a process while the laptop sleeps are schedules and "needs input" delivery. They are not a reason to stand up a public cloud, and they are not a reason to upload the working tree to someone else's container. Codex already shows the failure mode: a local scheduled task dies when the app closes, and a cloud continuation cannot see the computer's files ([Scheduled tasks](https://developers.openai.com/codex/automations); [Projects and chats](https://developers.openai.com/codex/projects)). Claude's answer is to move the agent loop to Anthropic and keep Desktop as a broker. Flynncode's answer is the machine the user already named.

Extend the routines plugin so a routine can target either the desktop sidecar or a Flynncode server on deepthought. The laptop path keeps today's rule: the app must be running, the run uses the local sandbox, and the result lands in the same review and activity inbox as a manual session. The deepthought path is for work that should survive sleep: a checkout that lives on that host, the same server the desktop can already attach to through Settings servers, and no new placement vocabulary. Do not invent a cloud environment image. Do not transfer browser sign-ins or the laptop VPN into that host. If a routine needs the laptop's files, it waits, the way a Codex local task waits. Cadence should grow from `dailyAt` toward the RRULE flexibility Codex documents, still inside the existing plugin. Webhook triggers for Gmail and Slack are out. They are the OpenAI cloud feature that is not even in the Codex desktop app, and they pull other companies' inboxes into the design.

Phone control should follow Codex remote control, not Claude's cloud session. Remote control drives the connected computer. It does not run the worktree on the phone ([Worktrees](https://developers.openai.com/codex/environments/git-worktrees)). The LAN gateway is that path when the phone and the desktop share a network. When they do not, deepthought can hold a self-hosted notifier and a reverse reach to the user's own server, so a "needs input" event leaves the house without Flynncode operating a push platform. Do not build a native phone app, a public share host, or a multi-user review room. The in-app review pane stays the review room. Session share stays a view link until someone asks for something else.

Build order is the loop, then reach, then the awake half. First, make an existing sandbox worktree disposable per session, with an explicit handoff back to the primary checkout, and make the existing review comments a follow-up the model is asked to address, with last-turn scope and hunk revert. Second, add the activity states — running, needs input, blocked — onto dispatch and the current notification path, including routine runs. Third, add the browser pane beside that review, annotations included, and a global quick-entry composer on the deep-link path that already exists. Fourth, point selected routines at deepthought and add on-disk memories, off by default, with secret redaction, never a synced belief store. Computer use comes after the browser works, off by default, per-app, and forbidden from approving its own permission prompts. Skip voice, Sites, cloud agent loops, screen-history memory, vendor import, and pane pop-out until the loop is the thing a user would miss.

Two limits should stay visible in the design. Linux Codex was still a preview on 11 August 2026, and no later changelog entry in the fetched log promoted it; Claude computer use and dictation are absent on Linux ([Changelog, 2026-08-11](https://developers.openai.com/codex/changelog); [Install Claude Desktop](https://support.claude.com/en/articles/10065433-install-claude-desktop)). Flynncode's Linux desktop cannot treat either vendor as a finished spec for those tools. And no September 2026 page states that either desktop app runs a turn with the network down. Flynncode can, because the router already ranks local models. That is the advantage to protect while copying their supervision loop.

## Conclusion

The vendors spent 2026 discovering that a coding desktop is a supervisor, then spending the rest of the year attaching cloud products to it. The reviews that watched the work still praise isolation and the review queue. Anthropic's October cutover says the local agent loop was the part they were willing to give up. Flynncode should take the opposite trade: keep inference and the workspace on machines the user controls, and spend the next design on the return path those reviews named — handoff, a comment that becomes the next turn, and an inbox for runs that need a human — because that path is the one this repo has not finished, and almost everything around it is already on disk.
