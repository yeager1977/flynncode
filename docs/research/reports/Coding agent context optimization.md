# Pin, defer, compact: Flynncode's token playbook

Every serious coding agent now spends more tokens on its harness than on the user's task, and all four major harnesses — Claude Code, Codex, Meta's Muse Code, and xAI's Grok Build — converge on the same six-part answer: compaction checkpoints, capture-time tool-output caps with disk spill, progressive disclosure of instructions/skills/tools, subagent context isolation, prompt-cache-aware prompt architecture, and cheap-model routing with token observability. What separates them is *where* they push the economy: **Claude Code** makes prompt-cache preservation the governing product invariant and adds idle-time compaction before cache expiry; **Codex** moves economy into a co-trained model (256-line reads, multi-window "Memento" compaction) plus a harness-side "world state" that survives compaction; **Muse** keeps the conversation small by moving knowledge outward — index-only memory, turn-scoped skills, notify-only messaging — at the price of four always-on observer agents; and **Grok Build** leans on markless automatic caching (0.25× rate), server-side compaction, and notably omits ingest-time tool-output truncation. For Flynncode the inventory is encouraging: the V2 session core already implements the skeleton — threshold compaction with a rigid template, 50 KiB tool-output spill, skills loaded body-on-demand, durable steer/queue, and an `auto` cache policy — but lacks idle compaction, a cheap-model summarizer, any token-budget cap on tool schemas or the instruction chain, and any token observability at all. The highest-value moves are cache-boundary work (idle compaction, stale-tool-result eviction at cache-invalidating boundaries) and a `/context`-style token ledger, all gated on the V2 core so the end-of-life V1 path inherits nothing new.

## Executive summary

- **Six families define the state of the art**, and all four agents implement nearly all of them as of October 2026: compaction/checkpoint summaries, capture-time tool-output truncation with disk spill, progressive disclosure of heavy catalog objects (skills, tool schemas, instructions, memory), subagent context isolation, prompt-cache-aware prompt architecture, and cheap-model routing plus token observability ([taxonomy table below](#every-harness-taxes-the-same-six-ledgers)).
- **Claude Code's distinctive is cache discipline as a product invariant**: a four-layer static-prefix ordering, a hard rule against mid-session tool-set/model mutation, compaction that forks off the parent's static stack to keep the shared cache, and *default-on idle compaction* that compacts a 200k+ conversation after ~54 minutes idle so it finishes before the 1-hour subscription cache expires ([claude-code.md §2.2, §6.2](../research_notes/Coding%20agent%20context%20optimization/claude-code.md)).
- **Codex's distinctive is economy in the model, not just the harness**: models are co-trained with the 256-line output cap in place and themselves ask for ~200-line reads, and GPT-5.1-Codex-Max is "the first model natively trained to operate across multiple context windows" via compaction ([OpenAI blog, 2025-11](https://openai.com/index/gpt-5-1-codex-max)); the harness contributes a persistent *world state*, verbatim retention of up to 20k tokens of recent user messages across compaction windows, and a ≤32 KiB root→cwd AGENTS.md budget.
- **Muse's distinctive is pushing knowledge out of the conversation**: index-only memory injection (a `MEMORY.md` index plus up to 48 file *paths*, bodies read on demand), turn-scoped skill loading, batched tool-call commits, and three-way peer-message delivery where "Notify only" never touches the recipient's model context ([muse.md](../research_notes/Coding%20agent%20context%20optimization/muse.md)) — but its default-on quartet of observer agents *adds* a standing token bill.
- **Grok Build's distinctive is aggressive caching — and a known hole**: fully automatic, marker-free prefix caching at 0.25× input price with zero write fee measured in 128-token blocks; xAI's own cookbook shows a single dynamic timestamp line at the top of the system prompt collapses cache hits from ~87% to ~3% (2.3×–2.9× cost), and the harness itself has **no tool-output truncation at ingest** ([grok.md](../research_notes/Coding%20agent%20context%20optimization/grok.md)).
- **Flynncode (V2) already has the load-bearing parts**: threshold compaction (default 0.9, rigid ~620-token summary template, ≤8,000-token recent-tail checkpoint), 2,000-line/50 KiB tool-output truncation with 7-day disk spill (`packages/flynncode/src/tool/truncate.ts`), skills listed as names/descriptions with bodies on demand, subagents with isolated context, durable steer/queue, and `AUTO` cache policy caching tools, system, and latest user message ([flynncode-inventory.md](../research_notes/Coding%20agent%20context%20optimization/flynncode-inventory.md)).
- **The notable absences are four**: no idle/cache-aware compaction (Claude's biggest organ win), no cheap-model summarizer for V2 compaction (small models handle titles/summaries but not `summarize()`), no token-budget management of tool schemas or the unbounded AGENTS.md chain, and **no token observability whatsoever** — no `/context`, `/usage`, or cost ledger anywhere in V2.
- **Recommended opening moves, all V2-gated**: idle compaction in `packages/core/src/session/compaction.ts`; route compaction summarization through the existing small-model tier (`getSmallModel` + the Ollama router's `route_task`, a free-local-routing option none of the four vendors offers); revive the dead `compaction.prune` config as cache-boundary stale-tool eviction; an instruction/skill-listing byte budget in `packages/core/src/instruction-context.ts` and `packages/core/src/skill/guidance.ts`; and a per-turn token ledger surfaced as `/context`.

Four independently-designed agents converging on six cost families is a strong signal about the shape of the problem. Two convergence findings deserve emphasis beyond the table. First, **compaction triggers differ per-turn vs per-session**, not just in threshold: Codex and Muse separate end-of-turn compaction (post-turn threshold percentage, hook-vetoable) from pressure-triggered compaction, which matters once a harness must not interrupt a turn mid-flight. Second, **the two cache-expensives are the two server-side agents' flagship features**: Anthropic bills cached reads at 0.1× with a 1.25× write premium and TTL-based idle compaction; xAI bills cached reads at 0.25× with zero write premium and encourages it so much that its own cookbook warns compaction "cost more than it saved" at small-chat scale ([docs.x.ai cookbook](https://docs.x.ai/cookbook/examples/prompt-caching)).

## Where each agent is genuinely distinctive

### Claude Code: the cache-hit rate is a health metric, backed by an idle-compaction sweep

Claude Code's Apr 30 2026 engineering blog, "*Lessons from building Claude Code — Prompt caching is everything*," is the most explicit statement any vendor has given of treating the cache hit rate as a monitored product health measure — Anthropic "declares internal SEVs for regressions" on it ([claude.com/blog](https://claude.com/blog), cited in [claude-code.md §6.2](../research_notes/Coding%20agent%20context%20optimization/claude-code.md)). Three defaults follow from that and exist nowhere else in this set. **Idle compaction** (default-on since v2.1.299) compacts a 200k+-token conversation after ~54 minutes idle, sized to land before the 1-hour subscription cache expires — compaction invalidates the cache anyway ("doing it while idle means zero lost work"; `CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS` and `"idleCompaction": false` are the opt-outs). **Prompt-block immutability** is enforced architecturally: plan mode is a tool call inside an unchanged tool schema rather than a tool-set swap, optional tools appear as `defer_loading: true` stubs discoverable via tool search, and dynamic state arrives as `<system-reminder>` text appended to the next user message instead of edits to earlier blocks. The repo-to-company illustration of the startup block totals the fixed shelf at roughly 20% of a 200k window — system prompt ~4,200 tokens, project CLAUDE.md ~1,800, skill listing ~450, deferred MCP names ~120, auto-memory index ~680 ([claude-code.md §1.1](../research_notes/Coding%20agent%20context%20optimization/claude-code.md)).

The second distinctive is **`/rewind` checkpointed undo (v2.0.0)** as the *first* breaker against wasted context — the session-management article frames every turn's options as continue, `/rewind` (restore code + prompt state to a checkpoint), `/clear`, compact, or dispatch-to-subagent, steering users toward branching before burning the window on frantic summarization ([claude.com/resources, 2026-04-15](https://claude.com/resources/articles/using-claude-code-session-mgmt)). The third is **tool-result-level microcompaction**: a community reverse-engineering of the CLI describes old `Read`/`Bash`/`Grep`/`Glob` results being cleared mid-session and replaced by a `[Old tool result content cleared]` sentinel, with a "cached microcompact" variant using Anthropic's `cache_edits` API so clearing does not invalidate cache — **[COMMUNITY-UNVERIFIED]**, marked here as in the notes and not confirmed in official docs as of 2026-10-19 ([claude-code.md §2.3](../research_notes/Coding%20agent%20context%20optimization/claude-code.md)). What *is* official underneath: the API's `context_management` beta (`clear_tool_uses_20250919`, `clear_thinking_20251015`) clears stale tool uses/thinking server-side — an internal benchmark recorded **+29% search improvement with editing alone and ~84% fewer tokens on 100-turn workflows** — and the changelog confirms production Claude Code sends a `context_management` field on the wire and retries without it behind gateways ([platform.claude.com context-editing](https://platform.claude.com/docs/en/build-with-claude/context-editing), cited in [claude-code.md §7.1–7.2](../research_notes/Coding%20agent%20context%20optimization/claude-code.md)). Server-side compaction as "the primary strategy for long-running conversations" sits behind the same doc family; the `compact-2026-09-04` beta marker was only seen in a search snippet **[SNIPPET-UNVERIFIED]**.

### Codex: the model is half the harness, and world state is the other half

Codex's 2025–2026 strategy is unique in this set: the harness *co-trains* the model and the model co-optimizes the harness. OpenAI staff confirm in GitHub issues that the model is trained with the 256-line output truncation cap in place and accordingly requests bounded reads itself — "`sed -n '1,256p' file.rs`" — and reads "only ~200 lines at a time to prevent filling the context window" ([issue #5913](https://github.com/openai/codex/issues/5913), [issue #8982](https://github.com/openai/codex/issues/8982), per [codex.md](../research_notes/Coding%20agent%20context%20optimization/codex.md)). GPT-5.1-Codex-Max is "our first model natively trained to operate across multiple context windows" through compaction ("Memento"-strategy in telemetry), with a stated **30% reduction in thinking tokens at equal effort on SWE-bench Verified** ([openai.com/index/gpt-5-1-codex-max](https://openai.com/index/gpt-5-1-codex-max)). The harness-side counterpart is unusual too: compaction *retains up to 20k tokens of real user messages verbatim* (newest-first, images dropped), appends a "CONTEXT CHECKPOINT COMPACTION" handoff summary built to a fixed template, and rebuilds a **world-state baseline** so notes/history "persist across windows" while message items in the current window are cleared ([codex-rs/core/src/compact.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/compact.rs), cited in [codex.md compaction section](../research_notes/Coding%20agent%20context%20optimization/codex.md)).

Defaults are documented and mostly favorable to a fork reading them: the tool-output mechanism has moved from hardcoded 10 KiB/256-line truncation to **token budgets with a "standard 20% serialization allowance"** and per-tool overrides (`tool_output_token_limit`, `mcp_servers.<id>.tools.<tool>.output_token_limit`); the AGENTS.md instruction chain is flattened root→cwd once per run into a shared **32 KiB budget** (`project_doc_max_bytes`), skipping empty files and truncating at the budget edge ([learn.chatgpt.com config reference](https://learn.chatgpt.com/docs/config-file/config-reference.md), cited in [codex.md](../research_notes/Coding%20agent%20context%20optimization/codex.md)); skills are the only just-in-time object with a **2%-of-window catalog budget capped at 10,000 tokens**. Cheap routing is *configured, not automatic*: `agents.default_subagent_model` and `default_subagent_reasoning_effort` steer spawned work to smaller models, plus per-mode effort presets (plan-mode override, compaction picks its own effort, optional `review_model`). Two cautionary details for adopters: compaction retries trim history from the *head* specifically "to preserve cache (prefix-based)" — mid-trim would multiply re-read cost — and **idle compaction is still only an open feature request** as of Aug 2026 ([issue #40924](https://github.com/openai/codex/issues/40924)), a direct comparison point with Claude Code's shipped default.

### Muse: economy by keeping knowledge out of the conversation — with an always-on observer tax

Muse Code (Meta, beta 2026-08-05, closed binary + open SDK at v1.4.x) applies progressive disclosure to the widest range of objects. Memory enters the model as **an index only**: "MEMORY.md plus a list of the other Markdown files (their paths, not their contents), up to 48 files," read on demand, with three scopes (personal-project outside the repo, committed `.agents/memory/`, machine-wide) built to be clone-shared; Meta explicitly flags the repo's MEMORY.md as a prompt-injection surface ([dev.meta.ai/docs/muse-code/configuration](https://dev.meta.ai/docs/muse-code/configuration), cited in [muse.md](../research_notes/Coding%20agent%20context%20optimization/muse.md)). Skills load "**only for the turn you invoke**" and are not re-reminded in later turns of the same session (v1.4.6); a `--preset empty` session ships no built-in tools, and MCP toolsets narrow by name/glob. Interaction-level economy is the most novel: peer-session messages deliver three ways — **Steer** (join the active turn), **Queue** (next turn), **Notify only** ("show and record the message without adding it to the recipient model's context") — and subagent results "drain back to the parent automatically once the parent's turn is idle" ([muse.md](../research_notes/Coding%20agent%20context%20optimization/muse.md)). Compaction checkpoints are atomic with the compaction itself ("cannot be written → compaction skipped and retried," v1.4.7), and resumes restart "from their latest compaction instead of rereading most of the session log" (v1.4.6).

The honest cost side matters for anyone copying the design: **all four persistent observer agents — memory recall, skill recall, goal tracking, verification — are on by default, and each makes its own model calls**, a standing overhead the docs acknowledge ("adds token usage in addition to the main session"), and one modern mitigation shows the harness knows the problem: auto-review escalates to the human after a reviewer burns 15 steps without deciding (v1.4.8). Independent reception echoes it — "concerns over token consumption" appear in an Oct 2026 brief ([OODAloop, 2026-10-13](https://oodaloop.com/briefs/technology/metas-zuckerberg-and-alexandr-wangs-high-stakes-bet-on-ai-agents)). Pricing-side economy exists too ($0.15/1M cached input; a "contributor" mode rated by tokens in a rolling 5-hour window rather than request count), but be careful about third-party republished prices ([muse.md flags one](../research_notes/Coding%20agent%20context%20optimization/muse.md)). The system prompt itself is not published; whether the Model API's "Tool search" capability is used inside the CLI's own request path is unconfirmed in the notes.

### Grok Build: caching so cheap that folding tool output is "someone else's job"

Grok Build (xAI, launched May 2026, open-sourced Apache-2.0 July 2026 at ~27.4k stars) is the closest structural comparable to Flynncode: same surface (AGENTS.md, hooks, MCP, skills, subagents, plan mode), and its THIRD-PARTY-NOTICES even disclose **in-tree source ports of `openai/codex` and `sst/opencode` tool implementations** ([x.ai/news/grok-build-open-source](https://x.ai/news/grok-build-open-source), cited in [grok.md](../research_notes/Coding%20agent%20context%20optimization/grok.md)). Its economics rest on the API: **fully automatic marker-free prefix caching, cached tokens at 0.25× input price, zero cache-write fee, metered in 128-token blocks**, with `prompt_cache_key`/`x-grok-conv-id` routing to the server holding the cache ([docs.x.ai prompt-caching](https://docs.x.ai/developers/advanced-api-usage/prompt-caching)). Two official engineering findings are worth internalizing as design constraints, not trivia: a *single dynamic line at the top* of the system prompt (a rotating timestamp) collapsed cache hits from **~87% to ~3%** and multiplied cost **2.3–2.9×** across the same workload; and compaction itself "cost more than it saved" at that chat scale, because compaction calls bill at output price — which refunds the vendor's choice to lean on cheap cached re-sends instead ([docs.x.ai cookbook](https://docs.x.ai/cookbook/examples/prompt-caching), cited in [grok.md](../research_notes/Coding%20agent%20context%20optimization/grok.md)). On the reasoning-reasoning-caching interaction: omitting `reasoning_content` from prior turns is "the top cause of cache misses" for reasoning models, so the stack replays encrypted reasoning verbatim.

The harness itself (v1.0.62, Oct 2026) compacts automatically near **~85% of the context window** into a nine-section "successor brief" (intent, files touched, errors, pending work, next step; third-party analysis of the open-source code via [blog.visionik.com](https://blog.visionik.com/how-grok-build-the-harness-works/)), exposes `/context-window` to select among a model's advertised window sizes (downsizing triggers an auto-compact), and shows *actually-served* models on smart-auto turns in the footer and `/usage` (v1.0.45). Token observability is the best-in-class of the four — `/context` breaks out pinned skill/MCP costs, `/usage` shows persisted per-turn token+cost, headless JSON includes per-prompt cost, and OpenTelemetry exports `grok_code.token.usage` split by input/output/**reasoning**/cache_read plus `grok_code.compaction` events with `tokens_before`/`tokens_after` ([tokenade.net guide](https://tokenade.net/en/articles/reduce-grok-cli-token-usage), cited in [grok.md](../research_notes/Coding%20agent%20context%20optimization/grok.md)). The structural hole is the counterexample worth studying: **hooks can only allow or deny tool calls; PostToolUse output cannot be rewritten and PreToolUse cannot fold it**, so a big test log rides into context at full size and only compaction can clear it — third parties route Grok Build through local proxies that fold tool results per request. Independent benchmarks bracket the lesson: a thin bare-API loop matched Grok Build 12/12 on micro-tasks at **19,981 vs 325,319 tokens (~16× harness tax, 93.9% of the bill pre-answer context)** ([terryli.ai, 2026-08-24](https://terryli.ai/posts/the-harness-is-part-of-the-token-bill/)), while inside real long-horizon work the same harness is the only one where the effort knob is monotone (84.1%→92.8% pass@1 low→xhigh) at ~3× token spend and 4.5-min median vs 16.3-min raw-API finishing times ([VulcanBench report, 2026-08](https://vulcanbench.com/assets/reports/vulcanbench-grok46-grokbuild-report.pdf)). Vendor-side model claims follow the "intelligence density" spine — Grok 4.5 at **4.2× fewer output tokens per SWE-Bench Pro task than Opus 4.8 (15,954 vs 67,020)** ([x.ai/news/grok-4-5](https://x.ai/news/grok-4-5)) — with partial independent corroboration of direction ([kingy.ai, 2026-07-08](https://kingy.ai/blog/grok-4-5-benchmarks-pricing-context-window/)).

## What Flynncode already ships — and the V1/V2 split that bounds everything

The inventory's headline is that **Flynncode's V2 core is closer to the state of the art than its reputation suggests**, and that all four gaps worth acting on are absent in V2, not V1. What already exists, with the mechanism: compaction triggers proactively at 0.9 of the model context and hard at context − 20,000, serializes the conversation into a pseudo-transcript with tool results capped at 2,000 chars, summarizes the head on the session's primary model (no tools, ≤4,096 output tokens) into a rigid Objective/Important-Details/Work-State/Next-Move template merged with a prior summary, and keeps a ≤8,000-token `<recent-context>` tail — the same "summary + recent window" architecture as Codex's world state minus the verbatim user-message retention ([packages/core/src/session/compaction.ts](../packages/core/src/session/compaction.ts), [packages/core/src/session/runner/llm.ts](../packages/core/src/session/runner/llm.ts)). Capture-time truncation matches Claude Code's persistent-to-disk pattern: 2,000 lines / 50 KiB with a 7-day-retention spill directory and a preview+hint left in the tool result ([packages/flynncode/src/tool/truncate.ts](../packages/flynncode/src/tool/truncate.ts)). Skills appear only as name/description listings with bodies on demand (`packages/core/src/skill/guidance.ts`), the system-context algebra announces `update(...)`/`removed` diffs the way Claude's `<system-reminder>` pattern does (`packages/core/src/system-context/`), subagents carry their own context with a restricted `explore` agent, durable steering/queueing promotes at safe boundaries (`packages/core/src/session/input.ts`), and the native LLM route applies cache hints for tools, system, and the latest user message plus an OpenAI `promptCacheKey` ([packages/llm/src/cache-policy.ts](../packages/llm/src/cache-policy.ts), [packages/llm/src/route/client.ts](../packages/llm/src/route/client.ts)).

The V1 pedigree matters for scoping, because the two generations overlap unevenly. V1 still runs its own compaction (prune/summarize with message reordering, protected skill outputs, 2,000–15,000-token preserve windows), its own instruction resolver (first-match-wins chain instead of V2's walk-all chain), V1-only plan-mode *synthetic reminders*, and provider-specific ~2,000–3,800-token system-prompt `.txt` files (`packages/flynncode/src/session/prompt/`) — one of which, `plan-reminder-anthropic.txt`, the inventory's grep found orphaned with zero imports. Two flagged V1 gaps are live bugs the inventory documents with file/line confidence: **the V1 AI-SDK path injects no cache hints at all** (cache tokens are only accounted, in `packages/flynncode/src/session/llm/ai-sdk.ts`), and the `compaction.prune` config key is parsed and then dropped — V2's `settings()` merges only auto/buffer/keep.tokens/threshold, so turn-by-turn eviction of old tool outputs happens nowhere ([flynncode-inventory.md §2](../research_notes/Coding%20agent%20context%20optimization/flynncode-inventory.md)).

What is **notably absent** across both generations, in order of weight: any token observability (no `/context`, `/usage`, per-turn ledger, or OTel export — the runner publishes LLM events but nothing aggregates or renders them); any token-budgeted pruning of tool *schemas* or MCP lists (materialization is permission-filtered only, so every permitted tool's schema enters every turn — the family where Claude's default-on MCP deferral and Codex's catalog economy have no Flynncode answer); any idle or cache-aware compaction; any cheap-model use inside V2 compaction (the small-model tier exists — titles, summaries, permission pre-review via `getSmallModel` + the `experimental.provider.small_model` hook touched by the Ollama router — but V2 `summarize()` streams from the primary model); any cap on the instruction chain (V2 inlines *every* matching AGENTS.md in full, unbounded — precisely the object Codex budgets at 32 KiB); reasoning-effort presets per mode (relevant since thinking tokens bill as output); and a retry/identical-call dedup guard (explicit TODO in the runner). Also thinner than peers: the environment block carries four facts (dir, root, git-repo, platform) versus Claude's branch/status/recent-commits block — an instructive, deliberate smallness worth noting rather than "fixing" reflexively. Finally, a category Flynncode alone has: routing subtask tokens through **free local models** (Ollama router `route_task`, [packages/flynncode/src/plugin/ollama-model-router/index.ts](../packages/flynncode/src/plugin/ollama-model-router/index.ts)) — a spend-zero lane none of the four vendors offers its users.

## The adoption backlog: quick wins first, all this work belongs in V2

Every structural bet here assumes AGENTS.md's own posture: V2 in `packages/core/src/session/**` is the strategic path, V1 is in managed decline. Nothing below should land in the V1 pipeline except the two cache-token accounting fixes noted as legacy caveats, and anything touching history layout must account for the V1→V2 migration so V2 features don't fork — the honest gate each item carries.

**Quick wins (days, local files, no wire-format risk):**

1. **Idle compaction before cache expiry** — port Claude Code's v2.1.299 default: when a session idles with estimated tokens above a floor (~75% of window to start), run compaction *while idle* so the next request starts on a fresh cheap prefix and the invalidation costs nothing. Where: compaction trigger site in `packages/core/src/session/runner/llm.ts` plus an idle-observer in `packages/core/src/session/execution.ts`; config knob beside existing `compaction.{auto,threshold}` in `packages/core/src/config/compaction.ts`. Effort: small-medium; needs an idle definition (SessionExecution already coordinates drains). It is the single highest-leverage cache win because Flynncode already pays for compaction on the same primary model and already has the machinery — this reuses it at the moment it is free.
2. **Summarize V2 compaction with the small-model tier** — `summarize()` currently streams from the session model (`packages/core/src/session/compaction.ts`), while a small-model pathway already exists for titles/summaries (`packages/flynncode/src/provider/provider.ts` `getSmallModel` callers; `experimental.provider.small_model` hook plumbing in `packages/flynncode/src/plugin/ollama-model-router/index.ts`). Rationale: Codex's compaction selects its own effort and Muse's reviewer is capped for the same reason — compaction is a fixed-format, low-agency task. With the router, this can be a *free local model with zero network dependence*, which none of the four can match. Effort: small; add a fallback to the primary model on quality/size failure so the path degrades safely.
3. **Instruction-chain budget + listings hardening** — cap the V2 instruction source at a configurable byte budget (Codex's 32 KiB is a proven default) with deterministic truncation (head-first, skip-empty ordering as Codex does), and truncate skill/reference listing descriptions (Claude's 1,536-char convention). Where: `packages/core/src/instruction-context.ts`, `packages/core/src/skill/guidance.ts`, `packages/core/src/reference/guidance.ts`. Effort: small — but it *changes the system prompt layout*, so verify the `AUTO` cache-policy benefit survives (deterministic budgets keep the prefix stable; a random pick would not). Ship an error/notice on overflow like Claude's memory-write limit rather than silently dropping files' tail. Effort: small-medium once the cache-stability test is included.
4. **Token observability: a `/context`-class ledger** — aggregate what the runner already publishes (`packages/core/src/session/runner/publish-llm-event.ts`, usage accounting in `packages/llm/src/route/client.ts`) into per-turn totals split input/cached-read/output/reasoning, plus a per-source context-size breakdown (system sources via `SystemContextRegistry.load`, tools via `tools.materialize`, instructions, history) exposed as a snapshot endpoint and a `/context` command surface. Rationale: Grok Build's observability is the best in class and Terry Li's 16× harness-tax study makes the case that un-instrumented harness spend stays invisible. Effort: medium; do *before* the bigger structural items because it measures them.
5. **Environment enrichment, deliberately capped** — extend `packages/core/src/system-context/builtins.ts` `core/environment` with git branch + a short status line (Claude's block also carries recent commits; branch + status is where the grounding value concentrates). Costs ~100–300 tokens/turn but is static per session, so cache-safe. Effort: trivial.

**Structural changes (design-first, wire-cache-sensitive):**

6. **Stale-tool-result eviction at cache-boundary moments ("microcompaction")** — revive the dead `compaction.prune` config as a scheduled pass that clears old tool results (and rewrites history rows) *only at points where the cache is being invalidated anyway* — immediately before compaction fires or at clear session boundaries — replacing their keeping text with a bounded sentinel the way both Codex's world-state rewrite and Claude's [COMMUNITY-UNVERIFIED] microcompact describe. Where: compaction/history path in `packages/core/src/session/compaction.ts` + `packages/core/src/session/history.ts` (SQL selection already scopes rows to the post-compaction epoch; eviction can build on that). Structural because Claude's own caution holds for everyone: clearing inside a cached prefix destroys the cache's value — the trick is the boundary, not the mechanism. Effort: medium; flag `compaction.prune`'s V1 parse-drop as the precedent bug to avoid repeating.
7. **Token-budgeted/deferred tool loading** — the biggest gap against Claude (default-on MCP deferral at >10% of window) and Codex (20% serialization allowance). Options in matching order of effort: (a) size-aware subset in `tools.materialize(agent.info?.permissions, ...)` (`packages/core/src/tool/`) with a documented budget; (b) Claude-style stub tools — MCP tools enter as names-with-stub-schemas, resolved via an internal catalog tool. Structural because mid-session tool-set changes are the classic cache killer; Claude's answer (stubs + tool search, global system-prompt caching preserved) is the design to copy, not an ad-hoc swap. Effort: large; a budget-only (a) can land without the catalog machinery if tool-catalog churn is nil across a turn.
8. **Reasoning-effort presets per mode + subagent default model/effort** — parity with Codex's per-mode effort presets (`model_reasoning_effort`, plan-mode override) and `agents.default_subagent_model`. Where: agent definitions in `packages/core/src/plugin/agent.ts` (built-ins `BUILD_SYSTEM`, `PROMPT_EXPLORE`) + task tool spawning in `packages/core/src/tool/task.ts` and `packages/flynncode/src/tool/task.ts`, wired through the existing small-model hook. Rationale: reasoning tokens bill as output for every provider in these notes; Explore-style agents (Haiku-for-Claude) are the documented pattern. Effort: medium; requires per-provider effort plumbing in `packages/llm` and honest per-provider `unavailable` fallbacks.
9. **Token-budget reminder + overflow budget** — Codex's harness-injected reminder ("context window nearly exhausted … notes and history items will be persistent") and experimental `rollout_budget` (limit_tokens, reminders every 10% of limit) are cheap to port: same injection point as the existing `MAX_STEPS_PROMPT` synthetic message in `packages/core/src/session/runner/max-steps.ts` / `runner/llm.ts`. The runner TODO's retry/dedup guard (explicitly unchecked) belongs here too. Effort: small-medium.
10. **OpenTelemetry token export** — Grok's `grok_code.token.usage` (input/output/reasoning/cache_read) + `grok_code.compaction` (`tokens_before`/`tokens_after`) events, from the existing client/event plumbing. Effort: small-medium once item 4's ledger exists; skip until then.

**Do not adopt (with reasons):** the server-side compaction/context-management API betas are Anthropic- and OpenAI-wire-specific and half [SNIPPET-UNVERIFIED] in the notes; Muse's four default-on observers invert the cost case until a *single* opt-in observer exists; Grok Build's smart-auto model routing is undocumented behaviorally, so there is no spec to port; xAI-style marker-free caching is a provider property, not a harness feature. And the V1-only fixes (cache hints on the AI-SDK path in `packages/flynncode/src/session/llm/ai-sdk.ts`; the orphaned `plan-reminder-anthropic.txt`) are 20-minute hygiene items that should ride along with their eventual retirement rather than attract new design.

## Conclusion

Two reframings come out of this comparison. First, **the cache is the real window**: Claude's cache-hit SEVs, Codex's head-trim-to-preserve-cache, Grok's 87%-vs-3% timestamp experiment, and xAI's "compaction cost more than it saved" all point at the same invariant — a Flynncode prompt architecture should be judged not by what it puts in the first turn but by *how few times it invalidates the prefix later*, which is why the backlog leads with idle compaction and boundary-time eviction rather than any new shelf object. Second, **the four agents prove that harness tokens are mostly fixed-shelf debt, not behavior**: a thin loop matched Grok Build on quality at 1/16 the tokens on micro-tasks, while the same harness earned its bill on long-horizon work — so the honest Flynncode target is not minimalism but *amortization*: every fixed object (instructions, schemas, listings) must either shrink to a budget, load on demand, or pay rent by measurably reducing other spend, and the missing token ledger is what would let that argument be made. Flynncode's two sovereign advantages — a model router that can run subtask tokens on free local models, and a V2 core whose compaction/steer/epoch machinery already matches the architectural pattern the big four converged on — mean the gap is execution and observability, not architecture: items 1–5 are days, item 6 is the design decision of the quarter, and none of it needs a new provider wire.
