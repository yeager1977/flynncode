title: Hooks
description: Run your own commands at lifecycle points - tool use, permissions, session events, and compaction.
---

Hooks let you run your own commands at fixed points in a session's lifecycle: before and after tool calls, when a permission would normally prompt, when a session starts or ends, and around compaction. Hooks are declared in JSON configuration, run shell commands, MCP tools, HTTP endpoints or a model prompt, and can deny actions, ask for confirmation, rewrite tool input, block a prompt or a stop, or inject context. Hooks written for Claude Code also run, from Claude's settings and enabled Claude plugins: see [Claude Code hooks](#claude-code-hooks).

In-process extensions live in [plugins](/docs/plugins). Hooks are the file-based complement: they work in any language that can read JSON from stdin and print a response.

---

## Configuration

Hooks live under the `"hooks"` key of the config file. Each event maps to an array of groups; each group has an optional `matcher` and a list of handlers:

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": ".opencode/hooks/gate-push.sh", "timeout": 10 }
        ]
      }
    ],
    "UserPromptSubmit": [
      {
        "hooks": [
          { "type": "command", "command": ".opencode/hooks/project-context.sh" }
        ]
      }
    ]
  }
}
```

Hook groups merge across config layers (global, project, and managed policy): hooks from every enabled layer run in order. Setting `"hooks": { "disableAllHooks": true }` is a global kill switch covered in [Trust and the kill switch](#trust-and-the-kill-switch).

## Events

Fourteen events are available. They fall into four kinds:

- **Decision** hooks can deny a tool call, ask the user to confirm it, or rewrite its input. They block execution until they return.
- **Post** hooks run after a tool executed or failed. They can block or replace the tool result the model sees.
- **Blocking** hooks can stop a prompt from being admitted (`UserPromptSubmit`) or refuse a stop and keep the turn going (`Stop`, `SubagentStop`). Otherwise they behave like observe hooks.
- **Observe** hooks inject context or report; they cannot block execution.

| Event | Kind | Matcher matches on | Fires when |
|---|---|---|---|
| `PreToolUse` | Decision | Tool name | Before a tool call executes |
| `PermissionRequest` | Decision | Tool name | Instead of showing a permission prompt |
| `PostToolUse` | Post | Tool name | After a tool succeeded |
| `PostToolUseFailure` | Post | Tool name | Instead of `PostToolUse`, when a tool errors or is aborted |
| `Notification` | Observe | Type (`permission_prompt`, `question`, `idle`) | A permission prompt or a question waits for the user, or a root session goes idle after a turn |
| `SessionStart` | Observe | Session source (`startup`, `resume`, `clear`, `compact`) | A session is created |
| `SessionEnd` | Observe | (empty - matches all) | A session is removed |
| `PreCompact` | Observe | Trigger (`manual`, `auto`) | Before a compaction runs |
| `PostCompact` | Observe | Trigger (`manual`, `auto`) | After a compaction succeeded |
| `UserPromptSubmit` | Blocking | (empty - matches all) | A user prompt is about to be admitted, before the turn runs |
| `SubagentStart` | Observe | Agent type | A subagent session starts |
| `SubagentStop` | Blocking | Agent type | A subagent's turn ends on its own, before it returns its result |
| `Stop` | Blocking | (always `idle`) | A root session's turn ends on its own, before the session goes idle |
| `Interrupt` | Observe | (always `interrupt`) | The user interrupts the session |

`Stop` and `SubagentStop` run at the end of the prompt loop, only for a turn that ended on its own. They do not fire after a cancel, an error, a content-filter stop, a rejected permission, a `continue: false` halt or a compaction-only turn. A session with a `parentID` fires `SubagentStop`; a root session fires `Stop`.

`UserPromptSubmit` does not run for synthetic prompts: background-task results, shell and monitor notifications, peer messages, and `Stop` continuations.

## Handler shapes

Four handler types are supported: `command`, `mcp_tool`, `http` and `prompt`.

### command

A shell command, run via `sh -c` in the hook's working directory (the current project directory). The event payload is written to the hook's **stdin** as a single JSON object. The command inherits Flynncode's environment; no additional environment variables are injected. Fields from the payload cannot be templated into the command string - use `jq` or your language of choice to read stdin.

```json title="opencode.json"
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": ".opencode/hooks/guard.sh",
            "timeout": 10,
            "additionalContextLimit": 2000,
            "statusMessage": "Checking branch policy"
          }
        ]
      }
    ]
  }
}
```

Command options:

- `timeout` - in **seconds**. Default 600 (1 second for `SessionEnd`). See [Timings](#timings).
- `async` - set `true` to run detached from the turn; the hook's output is then ignored. At most 8 async hooks run concurrently per session.
- `additionalContextLimit` - truncate this hook's `additionalContext` output to that many characters.
- `statusMessage` - reserved for status display; it is part of the hook's trusted identity.

### mcp_tool

Calls a tool on a connected [MCP server](/docs/mcp-servers). The `input` object is a template: string values may contain `${field}` placeholders that are expanded from the event payload, including nested paths such as `${args.command}`. A template string that is exactly one placeholder, like `"${args}"`, keeps the referenced value's type (object, not stringified). The payload also gains two convenience keys: `tool_input` (the tool call arguments) and `tool_output` (the tool result, for `PostToolUse`).

```json title="opencode.json"
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "mcp_tool",
            "server": "policy",
            "tool": "check_command",
            "input": { "command": "${args.command}", "mode": "${permission_mode}" }
          }
        ]
      }
    ]
  }
}
```

### http

POSTs the hook input JSON (the same object a command gets on stdin, in the group's format) to `url`.

```json title="opencode.json"
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "http",
            "url": "http://127.0.0.1:8787/hooks/pre-tool",
            "headers": { "Authorization": "Bearer ${POLICY_TOKEN}" },
            "allowedEnvVars": ["POLICY_TOKEN"],
            "timeout": 10
          }
        ]
      }
    ]
  }
}
```

- `headers` - `$VAR` and `${VAR}` in header values are filled in only for names listed in `allowedEnvVars`; any other variable becomes an empty string.
- A 2xx response whose body is a JSON object is read exactly like "exit 0 with that JSON on stdout", in the group's format.
- A non-2xx status, a timeout, a network error, or a body that is not a JSON object is logged and ignored, in every format. Unlike a failing native command, an unreachable endpoint never denies. HTTP has no exit-2 equivalent.
- `timeout` - in seconds, default 60. `statusMessage` works as for `command`.

### prompt

Asks a model to judge the event. The model must answer `{"ok": boolean, "reason"?: string}`.

```json title="opencode.json"
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "prompt",
            "prompt": "Did the assistant finish every task the user asked for? Event: $ARGUMENTS",
            "timeout": 30
          }
        ]
      }
    ]
  }
}
```

- `$ARGUMENTS` in `prompt` is replaced with the hook input JSON. If it is absent, the input is appended to the prompt.
- `model` - `provider/model`. Without it the configured `small_model` is used, else the session's model.
- `ok: false` denies a `PreToolUse` or `PermissionRequest` call, blocks a `UserPromptSubmit` prompt, and refuses a `Stop`/`SubagentStop` with `reason` as the continuation. On other events it is logged.
- `ok: true`, a model error, or an answer that is not valid JSON expresses no opinion.
- `timeout` - in seconds, default 60. `statusMessage` works as for `command`.

## Input payload

Every hook receives one JSON object on stdin (for `mcp_tool` handlers, the same payload is used as the template source):

| Field | Present on | Description |
|---|---|---|
| `event` | all | The event name, e.g. `"PreToolUse"` |
| `sessionID` | all | The session the hook fired for |
| `cwd` | all | The directory the hook runs in |
| `tool`, `callID`, `args` | decision, PostToolUse and PostToolUseFailure events | The tool call: name, ID, and arguments object |
| `output` | `PostToolUse` | The tool's output |
| `error`, `isInterrupt` | `PostToolUseFailure` | The error text, and whether the call was interrupted (aborted) |
| `model` | `PreToolUse` and `PostToolUse` | The model driving the turn, when known |
| `permission_mode` | decision and PostToolUse events | The active permission approval mode, when known |
| `source` | `SessionStart` | One of `startup`, `resume`, `clear`, `compact` |
| `reason` | `SessionEnd`, `Stop`, `Interrupt` | `idle` on `Stop`, `interrupt` on `Interrupt`; on `SessionEnd` currently always `other` |
| `stopHookActive` | `Stop`, `SubagentStop` | `true` when this stop follows a continuation a stop hook forced |
| `message`, `notificationType`, `tool` | `Notification` | The notice text, its type (`permission_prompt`, `question`, `idle`), and the tool id for a permission prompt |
| `prompt` | `UserPromptSubmit` | The text of the admitted prompt |
| `trigger`, `phase` | `PreCompact` / `PostCompact` | One of `manual` / `auto`, and `pre` / `post` |
| `agentID`, `agentType` | `SubagentStart` / `SubagentStop` | The subagent session ID and agent name |

Observe events are session-scoped: `model` is only sent on `PreToolUse` and `PostToolUse`, and `permission_mode` only on decision and PostToolUse events. `PermissionRequest` payloads carry `permission_mode` but never `model`.

## Output contract

A hook communicates through its exit code and, on success, its stdout.

### Decision hooks (PreToolUse, PermissionRequest)

Exit code 0 with JSON on stdout:

```json
{ "behavior": "deny", "message": "Direct pushes to main are not allowed" }
```

- `{"behavior": "deny", "message": "..."}` - the call fails with `message` (default "Denied by hook"). In a deny, every other hook's context and rewrites are discarded.
- `{"behavior": "allow", "updatedInput": { ... }}` - the call proceeds with replaced arguments.
- `{"behavior": "allow", "additionalContext": "..."}` - the call proceeds; the text is added as context for the turn.
- `{"behavior": "ask", "message": "...", "updatedInput"?: { ... }}` - ask the user. See [The ask decision](#the-ask-decision).
- `{"behavior": "undecided", "additionalContext": "..."}` - no opinion; context is still carried.

On `PermissionRequest`, `updatedInput` is ignored: the hook may only deny or skip the prompt.

Other outcomes of a decision hook:

- **Empty stdout, exit 0** - no opinion (equivalent to `undecided`).
- **Exit code 2** - deny. The message prefers trimmed non-empty stderr, then stdout, then a generic fallback. This is the simplest way to block: print the reason to stderr and exit 2.
- **Any other non-zero exit, a timeout, a spawn failure, or non-empty stdout that is not valid decision JSON** (including valid JSON without a recognized `behavior`) - **fails closed**: the call is denied with a generic message.
- **MCP tool errors** for an `mcp_tool` decision hook also fail closed (deny).

When several decision hooks match, **deny beats ask, and ask beats allow**, regardless of order (deny > ask > allow > undecided); otherwise the first `updatedInput` rewrite wins and remaining contexts are joined with a blank line.

For `PermissionRequest`, hooks run after config permission rules - a config-level deny has already applied, and the hook only stands in for a prompt the user would otherwise see. A deny still wins over any allow, in every approval mode.

### The ask decision

A `PreToolUse` hook can return `ask`: native `{"behavior": "ask", "message": "..."}` or Claude `"permissionDecision": "ask"`. It forces the normal permission prompt for that call even when a rule or an earlier "always" approval would allow it, and even under accept-edits.

- There is exactly one prompt: the tool's own permission prompt, with its real patterns (the command, the file path) after any `updatedInput` rewrite. Tools without their own permission check get one prompt under the tool's id before they run.
- The hook's message is shown in the prompt (`metadata.reason`).
- The prompt cannot be skipped by another prompt's "always" answer, and it carries no "always" patterns: the app does not offer "Allow always", and an "always" reply from another client approves only this call.
- Config deny rules still deny. In `auto` approval mode the auto-reviewer answers it, as it answers every prompt; `PermissionRequest` hooks and the plugin `permission.ask` hook can answer it too.

### PostToolUse and PostToolUseFailure

Exit code 0. The hook may:

- Return `{"blockedOutput": "..."}` to **replace the model-visible tool result** with that text. An exit code 2 behaves the same, with the reason taken from stderr first.
- Return `{"additionalContext": "..."}` to append context to the turn.
- Return anything else (or plain text, or nothing): no effect.

Non-zero exits other than 2 and timeouts are warn-and-ignore: a post hook failing closed would only degrade the result, so it does not block.

`PostToolUseFailure` fires instead of `PostToolUse` when the tool body fails (an error, a permission denial or rejection, a sandbox violation) or the call is aborted (`isInterrupt: true`). A `PreToolUse` deny does not fire it, because the tool never ran. A block reason or `additionalContext` from the hook is appended to the error the model sees.

### Observe hooks

Exit code 0, JSON:

```json
{ "additionalContext": "Team conventions: tabs everywhere", "systemMessage": "Warn the user in the UI" }
```

- `additionalContext` - injected as model context, with placement per event (see below).
- `systemMessage` - written to the log as a warning; it never enters the model context and is not yet shown in the app.
- `continue` - `false` is honored by `PreCompact` (it skips the post-compaction auto-continue turn). On other native observe events it is parsed but has no effect (`SubagentStart` ignores it by design). Claude-format hooks honor it more widely; see [Claude output](#claude-output).
- `stopReason` - recorded in logs alongside `continue`.

Plain-text stdout is developer context: **on observe events, non-empty non-JSON stdout is promoted wholesale to `additionalContext`** (bounded by `additionalContextLimit` when set). Any valid JSON keeps its parsed behavior, and empty stdout stays a no-op.

Observe hooks never block: exit 2, other non-zero exits, and timeouts are logged and ignored.

### Blocking hooks (UserPromptSubmit, Stop, SubagentStop)

These accept everything observe hooks do, and can also block: exit 2 (stderr is the reason, then stdout) or `{"behavior": "deny", "message": "<reason>"}`. A Claude-format hook blocks with exit 2 or `"decision": "block"`, and a `prompt` handler with `ok: false`.

- **`UserPromptSubmit`:** the prompt is not admitted. No user message is written and no model call is made, and the app shows the reason in a toast. Over HTTP, `POST /session/:id/prompt_async` publishes a `session.error` whose message is `Prompt blocked by hook: <reason>`; the synchronous `POST /session/:id/message` and `/command` routes answer `422` with `{"name": "PromptBlockedError", "data": {"message": "<reason>"}}`.
- **`Stop` and `SubagentStop`:** the stop is refused. The reason is admitted as a synthetic user message (`Stop hook feedback:` followed by the reason; the app shows it as a compact "Background activity" divider) and the loop runs another turn. The next stop hook input has `stopHookActive: true` (`stop_hook_active` for Claude hooks). A `SubagentStop` block continues the sub-agent before it returns its result.
- **Cap:** at most **8** forced continuations per user prompt. After that the stop is allowed and a warning is logged; the hook still runs on that ninth stop. A new real prompt resets the count.
- A `Stop` hook runs inline before the session goes idle, so a slow hook keeps the session busy for its run. A cancel interrupts it.

## Where context goes

Observed `additionalContext` is placed differently per event:

- **Sticky (whole session):** `SessionStart`, `SubagentStart` (stored on the child subagent session), and `PostCompact`. These are stored per session, deduplicated, capped at 100 entries, injected into every assembled system prompt after the built-in sections, and cleared when the session is removed.
- **Per-turn:** `UserPromptSubmit` context rides on the admitted user message for that prompt only. `PreCompact` context is appended to that compaction's prompt only.
- **Report-only:** `SessionEnd`, `SubagentStop`, `Stop`, `Notification` and `Interrupt` - their context output is logged and discarded; nothing is stored. (A `Stop`/`SubagentStop` block reason is the exception: it becomes the continuation.)

`additionalContextLimit` (command handlers only) truncates context at every one of these surfaces, including promoted plain-stdout text.

## Matchers

Each group's optional `matcher` is a regular expression tested (unanchored, `RegExp.test`) against the match name for the event: the tool name for `PreToolUse`, `PermissionRequest`, `PostToolUse` and `PostToolUseFailure`; the notification type for `Notification`; the session source for `SessionStart`; the trigger for `PreCompact`/`PostCompact`; the agent type for `SubagentStart`/`SubagentStop`; and the idle/interrupt reason for `Stop`/`Interrupt`. Claude-format groups match differently; see [Claude input](#claude-input). `"Bash"` also matches `AnyBash`-like names because the pattern is unanchored.

- Omitted, empty, or `"*"` match everything.
- Invalid patterns never match (and never crash the call).

## Trust and the kill switch

A hook is executable code. Flynncode reviews it before running it.

**Hook identity.** Every hook's behavior fields (`matcher`, `command` or `server`/`tool`/`input`, `timeout`, `async`, `additionalContextLimit`, `statusMessage`) are canonicalized into a JSON hash (keys sorted, `undefined` dropped). For `command` hooks, any command token that resolves to a readable file inside the project root contributes that file's SHA-256 content hash to the identity. Editing the hook config, or editing a project script it runs, changes the hash: trust must be re-granted.

**Trust storage.** Granted hashes live in `~/.local/share/flynncode/hooks-trust.json` (override with `FLYNNCODE_HOOKS_TRUST_FILE`). Trust is granted through the settings UI or the server's hook trust endpoints, and listing/revoke endpoints expose hook summaries in the config API. Trust is per project: the same hook definition in another repository is a different hook. Trust checks happen before every spawn; untrusted hooks are skipped with a warning, never executed, and lookup failures read as untrusted (fail closed).

**Managed (MDM) hooks.** Hooks declared in managed/MDM configuration are trusted by policy: they run without per-definition review and cannot be revoked (revoke refuses managed hashes). Missing or unreadable managed config fails closed.

**Bypass flag.** The CLI flag `--dangerously-bypass-hook-trust` (environment equivalent `FLYNNCODE_BYPASS_HOOK_TRUST`) treats every hook as trusted for that one invocation, without writing trust state. It exists for automation; the review flow is preferred for interactive use. The flag is process-memory only and is never inherited by the commands, shells, or nested CLI processes a hook or session spawns.

**Kill switch.** `"hooks": { "disableAllHooks": true }` disables every hook from file configuration - including managed (MDM) policy hooks and Claude Code hooks - and cannot be re-enabled by the bypass flag. In-process plugin hooks are unaffected by this switch. Claude Code hooks have their own switches; see [Sources and switches](#sources-and-switches).

## Timings

- Every hook has a **timeout in seconds**. The default is 600 seconds for `command` (and `mcp_tool`) handlers and 60 seconds for `http` and `prompt` handlers. `SessionEnd` hooks are advisory with a 1 second default and a hard 3 second cap.
- On timeout a command hook's whole process group receives `SIGTERM`; after 3 more seconds it is sent `SIGKILL`, so orphaned grandchildren cannot hold pipes open.
- `timeoutMs` caps may also be applied programmatically; a per-hook `timeout` larger than the event's cap is clamped down.
- Handlers marked `"async": true` run detached. Their output is discarded (context, decisions, and blocking do not apply). At most 8 async hooks run concurrently per session; synchronous hooks are never queued behind them. Asynchronous hooks are cancelled when their session is removed.

## Claude Code hooks

Flynncode also runs hooks written for Claude Code. They join the same runner, tagged with the Claude format, and run **after** the native hooks of the same event.

### Sources and switches

| Source | Source id | Files |
|---|---|---|
| Claude user | `claude:user` | `~/.claude/settings.json`, `~/.claude/settings.local.json` (`hooks` key) |
| Claude project | `claude:project:<absolute .claude dir>` | `<dir>/.claude/settings.json` and `settings.local.json` for each project `.claude` directory from the worktree root down to the working directory |
| Claude plugin | `claude:plugin:<name@marketplace>` | `<installPath>/hooks/hooks.json` (`hooks` key) for every plugin set to `true` in `enabledPlugins` of `~/.claude/settings.json`, resolved through `~/.claude/plugins/installed_plugins.json` (version 2). The `user`-scope install is preferred, then a `project`-scope install for this project. |

Variables:

- `${CLAUDE_PROJECT_DIR}` (the project root) and, for plugins, `${CLAUDE_PLUGIN_ROOT}` (the plugin's install path) are expanded in `command` strings, braced or not, and are also set as environment variables.
- Plugin hooks also get `CLAUDE_PLUGIN_DATA=~/.claude/plugins/data/<plugin id with @ replaced by ->`.

Only hooks are imported. Permissions, env, model and other settings, and plugin commands, agents, skills and MCP servers are not.

Bad sources are skipped with a warning shown on the Hooks settings page and in the log: invalid JSON, an unknown event or handler type (Claude's `agent` type is not supported), a missing install path, or a plugin missing from `installed_plugins.json`. Other hooks are unaffected.

Switches, from widest to narrowest:

- `"hooks": { "disableAllHooks": true }` in Flynncode config turns off every hook, Claude hooks included.
- `OPENCODE_DISABLE_CLAUDE_HOOKS=1` turns off only the Claude sources. `OPENCODE_DISABLE_CLAUDE_CODE=1` turns them off too, with the rest of the Claude Code compatibility.
- Claude's own `"disableAllHooks": true`: in the Claude user settings it turns off every Claude source; in a project's settings it turns off that project source. The last value across `settings.json` and `settings.local.json` wins.
- `"claude_hooks": { "disabled": ["<source id>", ...] }` in Flynncode config skips the listed sources. Lists from every config layer are combined. Each source on the **Settings → Hooks → Claude Code** page has an on/off switch, which adds or removes its id in the global config file (`~/.config/flynncode/opencode.jsonc`). A source disabled in a project config stays off there.

**Trust.** Claude hooks go through the same [trust review](#trust-and-the-kill-switch) as native hooks. The source id is part of each hook's identity, and the settings page names the source of every hook awaiting review. A changed command is a new hook and needs trust again.

### Claude input

A Claude-format hook gets Claude Code's stdin fields:

| Field | Events |
|---|---|
| `session_id`, `transcript_path`, `cwd`, `permission_mode`, `hook_event_name` | all |
| `tool_name`, `tool_input`, `tool_use_id` | `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PostToolUseFailure` |
| `tool_response` | `PostToolUse` |
| `error`, `is_interrupt` | `PostToolUseFailure` |
| `prompt` | `UserPromptSubmit` |
| `source` (`startup`, `resume`, `clear`, `compact`) | `SessionStart` |
| `reason` | `SessionEnd` |
| `trigger` (`manual`, `auto`), `custom_instructions` | `PreCompact` |
| `stop_hook_active` | `Stop`, `SubagentStop` |
| `agent_id`, `agent_type` | `SubagentStart`, `SubagentStop` |
| `message`, `notification_type` | `Notification` |

Translation:

- **Tool names** use Claude's: `bash` → `Bash`, `read` → `Read`, `edit` → `Edit`, `write` → `Write`, `glob` → `Glob`, `grep` → `Grep`, `task` → `Task`, `question` → `AskUserQuestion`, and so on. MCP tools become `mcp__<server>__<tool>`. A tool with no Claude name keeps its Flynncode id.
- **`tool_input`** keys of translated tools are snake_case (`filePath` → `file_path`, `oldString` → `old_string`), at every depth.
- **`tool_response`** is `{stdout, interrupted}` for Bash, `{filePath, success}` for file writes and edits, and `{output}` otherwise.
- **`permission_mode`**: `manual` → `default`, `accept-edits` → `acceptEdits`, `auto` → `auto`.
- **`notification_type`**: `permission_prompt`, `elicitation_dialog` (a question) or `idle_prompt` (idle).
- **Matchers** test the Claude name: a plain name or an `A|B` list must equal the whole name (`Edit|Write`), any other matcher is an unanchored regular expression (`mcp__.*`). On `Notification` they test the Claude `notification_type`; on `UserPromptSubmit` and `Stop` they are ignored.

### Claude output

| Result | Meaning |
|---|---|
| Exit 2 | Depends on the event, below. |
| Exit 0, stdout is a JSON object | Claude's JSON fields, below. |
| Exit 0, plain text | Added as context on `SessionStart` and `UserPromptSubmit`; ignored elsewhere. |
| Any other exit, a timeout, or a spawn failure | Logged and ignored. Claude hooks never deny on error. |

Exit 2:

- `PreToolUse`, `PermissionRequest`: deny the call; stderr goes to the model.
- `PostToolUse`, `PostToolUseFailure`: stderr goes to the model.
- `UserPromptSubmit`: block the prompt; stderr is shown to the user.
- `Stop`, `SubagentStop`: refuse the stop; stderr is the continuation reason.
- Other events: stderr is logged.

JSON fields:

- `hookSpecificOutput.permissionDecision` (`allow`, `deny`, `ask`) with `permissionDecisionReason`, on `PreToolUse`.
- `hookSpecificOutput.updatedInput` on `PreToolUse`, translated back to Flynncode argument names. Keys that don't map are dropped with a warning.
- `hookSpecificOutput.additionalContext` on `SessionStart`, `UserPromptSubmit`, `PostToolUse` and `PostToolUseFailure`.
- `decision: "block"` with `reason`: on `PostToolUse` the tool output is kept and the reason is appended on a marked line; on `UserPromptSubmit` the prompt is blocked; on `Stop`/`SubagentStop` the stop is refused.
- `continue: false` with `stopReason`: on `PreToolUse` and `PermissionRequest` the call is denied, and on `PostToolUse`/`PostToolUseFailure` its result is blocked; the turn then ends after that tool step. On `UserPromptSubmit` the prompt is blocked. On `Stop`/`SubagentStop` it outranks `decision: "block"`, so the stop goes through.
- `systemMessage`: logged as a warning. It is not yet shown in the app.

### Transcript file

`transcript_path` points to `<data dir>/claude-transcripts/<sessionID>.jsonl` (the data dir is `~/.local/share/opencode`), written in Claude Code's transcript line format: one JSON object per message with `type` (`user` or `assistant`), `message` (`role` and `content` blocks: `text`, `tool_use {id, name, input}`, `tool_result {tool_use_id, content, is_error}`), `uuid`, `parentUuid`, `timestamp`, `sessionId` and `cwd`.

- It is brought up to date right before a Claude-format hook runs, and exists only for sessions where one ran. New messages are appended; the last written message is kept in `<sessionID>.cursor`. A message still streaming is written on a later update.
- Tool names and inputs use the Claude translation above.
- It is deleted with its session and swept with the rest of the history retention.
- A failed write is logged, and the hook still runs with the last good path, or an empty `transcript_path`.

## Examples

### PreToolUse: deny pushes to a main branch

```json title="opencode.json"
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": ".opencode/hooks/guard-main.sh",
            "timeout": 10
          }
        ]
      }
    ]
  }
}
```

```bash title=".opencode/hooks/guard-main.sh"
#!/bin/sh
# The hook runs with cwd set to the project directory, so git works here.
branch=$(git rev-parse --abbrev-ref HEAD)
command=$(printf '%s' "$(cat)" | jq -r '.args.command')
case "$command $branch" in
  "git push "*|"git push"*" main")
    cat <<'EOF'
{"behavior":"deny","message":"Direct pushes to main are not allowed. Use a pull request instead."}
EOF
    ;;
esac
```

A bare `git push` on the main branch denies the Bash call with the hook's message. Every other case prints nothing on stdout and exits 0, which is a no-op.

### PostToolUse: format what the model just wrote

```json title="opencode.json"
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "^(Edit|Write)$",
        "hooks": [
          { "type": "command", "command": ".opencode/hooks/fmt.sh", "timeout": 30 }
        ]
      }
    ]
  }
}
```

```bash title=".opencode/hooks/fmt.sh"
#!/bin/sh
# The changed file is in the payload's args; formatter runs in the repo root.
jq -r '.args.filePath' | xargs oxfmt 2>/dev/null || jq -r '.args.filePath' | xargs prettier --check
if [ $? -ne 0 ]; then
  printf 'formatter rejected the edit: check formatting manually' >&2
  exit 2
fi
```

An exit code 2 replaces the model-visible tool result with the stderr reason, so the model knows the edit is not formatted.

### UserPromptSubmit: inject project context per turn

```json title="opencode.json"
{
  "hooks": {
    "UserPromptSubmit": [
      {
        "hooks": [
          { "type": "command", "command": ".opencode/hooks/context.sh", "additionalContextLimit": 4000 }
        ]
      }
    ]
  }
}
```

```bash title=".opencode/hooks/context.sh"
#!/bin/sh
echo "Current deployment target: staging (see deploy/README.md)."
```

Plain stdout is promoted to context and rides on this prompt only.

## Relationship to plugins

Plugin hooks (in-process `tool.execute.before`/`tool.execute.after` handlers and the `permission.ask` hook) run alongside file hooks. Two interactions are worth knowing:

- On `PreToolUse`/`PermissionRequest`, a plugin-declared decision runs first, and a plugin **deny** short-circuits before file hooks and rewrites.
- The plugin `permission.ask` hook is consulted **before any approval-mode shortcut**: a plugin deny (or fail-closed verdict) wins in every mode, while allow/ask fall through to mode shortcuts, the `PermissionRequest` hook, and the pending prompt. This is Phase-1 landed behavior.
